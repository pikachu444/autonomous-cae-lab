# User-result acceptance and evidence boundaries

| ID | Scenario and required outcome | Requirement mapping |
|---|---|---|
| AC-D01 | Given Windows and the selected tool, when a supported document/file is opened, then the correct native desktop editor opens without a web dashboard or unrelated CAD/AI installation. | REQ-DESKTOP-001-001, REQ-DESKTOP-001-002 |
| AC-D02 | Given every required research family, when a developer follows the functional spec, then input/output, units, edits, failures, recovery, save/reopen and implementation/reuse/support boundaries require no invented core interaction. | REQ-DESKTOP-001-003, REQ-DESKTOP-001-004, REQ-DESKTOP-001-013 |
| AC-D03 | Given editable source/screens/prototype, when the reviewer opens the artifacts, then representative Material, Pre/contact, Post, PDE/Numerical, Runner, Expert and Study tasks can be followed through success and correction/cancel/reopen states. | REQ-DESKTOP-001-005 |
| AC-D04 | Given invalid required input, when export/run is requested, then execution is blocked at the offending target while draft save/reopen and correction remain possible. | REQ-DESKTOP-001-006 |
| AC-D05 | Given prior failed/completed attempts and edited current inputs, when a new run/adoption is requested, then old inputs/results remain bound to old IDs and stale candidate adoption requires explicit correction. | REQ-DESKTOP-001-007 |
| AC-D06 | Given an active run, when the editor closes or cancellation is requested, then close/save and requested/terminal cancellation remain distinct and partial/failed records survive recovery. | REQ-DESKTOP-001-008 |
| AC-D07 | Given failed saving or moved/changed source dependencies, when repair/reopen is attempted, then prior commit and current draft survive; identical-content repair and changed-content revision are distinguished. | REQ-DESKTOP-001-009 |
| AC-D08 | Given old numerical failure/UNKNOWN qualification, when UI/CI/design passes, then the old threshold and unknown release requirements remain and no physical approval is inferred. | REQ-DESKTOP-001-010 |
| AC-D09 | Given the selected planning/product tools, when usage and distribution are reviewed, then additional spending is zero and unavailable free/backend paths remain identified. | REQ-DESKTOP-001-011 |
| AC-D10 | Given actual Pro-authored artifacts and independent review, when design or an implementation delivery is presented, then authorship, applied corrections, actual checks and unresolved decisions are explicit. Follow the latest assignment: routine assigned development needs no repeated approval, while historical implementation authorization does not restart later stopped or planning-only work. | REQ-DESKTOP-001-012 |
| AC-D11 | Given the backlog/trace table, when a feature is selected, then its requirement and screens lead to existing/new code targets, user acceptance, verification purpose/timing/prerequisites and exact reused evidence. | REQ-DESKTOP-001-014 |
| AC-D12 | Given the review prototype at actual desktop size, when a user follows the representative task, then selection, values/units, state, errors and next action remain apparent without developer guidance or long explanatory text; resize, keyboard and contextual panels preserve the task. | REQ-DESKTOP-001-015, REQ-DESKTOP-001-005 |

Planning interactions and DEMO values are not actual solver/provider acceptance.
Windows GUI completion needs actual native interaction; offscreen widget captures
only substantiate their stated rendering/self-check scope. Physics claims need
reference comparison for their supported response and original tolerances.

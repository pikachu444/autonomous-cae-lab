# 공학 데스크톱 앱의 기반과 개발 복구안

2026-10-18. 실제 Pro의 교정안과 Astra Extra High의 최종 독립 검토를 Codex가 통합했다.
다른 GUI 대화의 원문과 실제 소스를 대조해 기반·공통 요소·담당·첫 종료조건을 확정한 실행안이다.
이 문서는 제품을 고쳤다는 보고가 아니다. 구현 현황·현재 배정은 [CURRENT_STATE](../CURRENT_STATE.md),
전체 기능과 지원 범위는 [DEVELOPMENT_ITEMS](DEVELOPMENT_ITEMS.md)에 있다.

## 1. 바꾸는 개발 방식

기존 GUI를 그대로 두고 색과 문구를 고치는 방법으로 복구하지 않는다. 완성형 공학 앱의
실제 기반을 비교하고, 가져올 명령·선택·탐색·속성·작업면과 기존 계산 코드의 연결을 먼저 정한다.
정적인 SVG/PNG를 더 그리는 작업은 중단했다. 다음 기술 확인의 대상은 실제로 조작할 수 있는
프로그램 뼈대다. 빈 창과 장식 버튼을 만드는 것으로 끝내지 않는다.

계산·문서·실행의 기반을 보존하는 것과 GUI 층을 교체하는 것은 별개다. 기존 GUI를 유지하는
비용도 공통 명령·선택 연결·긴 폼·앱 간 불일치를 고치는 양을 포함해 평가한다. 공개 앱은
화면만 참고하는지, 일부 소스를 가져오는지, 앱을 포크해 작업 환경을 유지하는지 구별한다.

## 2. 제품의 모습

제품은 Windows 로컬에서 각각 실행할 수 있고 필요한 자료를 주고받는 공학 도구군이다.
기본 진입에서 최근 작업과 도구를 고를 수 있지만, 이 목록 화면이 전체 제품의 작업면은 아니다.
각 앱은 자기 파일을 직접 열고 자기 작업을 끝낸다. CAD/FE는 FreeCAD, 3D 후처리는 ParaView의
실제 창을 쓴다. 별도 OS 창을 하나의 임베딩된 창처럼 설명하지 않는다.

| 앱과 사용자 이름 | 탐색·메뉴·명령 | 중심 작업면과 선택 설정 |
|---|---|---|
| CAD/FE — 설계와 전처리 | FreeCAD 문서·Body·피처·Assembly·FEM 트리와 native 메뉴·도구 모음 | 실제 형상·메시·면/모서리 선택, 해당 객체의 Properties/Tasks. 재료·구속·힘·메시를 원 편집기에서 수정한다. |
| Post — 결과 분석 | ParaView pipeline·filter·표현·배열·시간·선택 명령 | Render/Chart/Spreadsheet View에서 같은 필드·성분·시각을 읽는다. 추가 측정 설정은 선택 대상에 맞춰 별도 보조창에서 연다. |
| Data — 자료 분석 | 자료·워크북·시트·열·처리 단계 탐색, 열/그래프/변환 명령 | 워크시트와 연결 그래프. 셀·행·범위 선택이 같은 점·구간을 가리키고 열 대응·단위·제외·변환을 직접 편집한다. 원자료 값은 보존한다. |
| Material — 재료 연구 | 시험 목록과 프로토콜·이력, 재료 법칙, 시험/재료/계산 메뉴 | 시험·계수 표와 큰 관측/예측/잔차 곡선. 선택 시험의 조건과 계수를 편집하고 평가·동정·별도 확인·채택을 구별한다. |
| PDE — 방정식 모델 | 장·식·영역·경계·mesh·방법·해의 모델 트리, 모델/방정식/해석 명령 | 수식 편집과 영역·mesh·해 또는 시간 곡선. 선택 경계와 조건의 식·값·단위가 같은 대상을 가리킨다. |
| Numerical — 수치 연구 | 평가기·변수·응답·제약·방법·후보 탐색, 계획/방법/후보 명령 | 변수·응답·후보표와 선택 후보의 곡선·목적 plot. 동정·DOE·최적화·UQ 등의 작업에 맞춰 설정과 결과가 바뀐다. |
| Simulation — 해석 설정 | native 해석 객체 또는 외부 deck/include·단계·집합·출력 탐색 | 지원 입력과 실행 설정을 편집한다. native 재료·하중은 FreeCAD에서 연다. 외부 입력은 지원되는 편집과 해당 위치의 진단을 제공한다. |
| Evaluation — 계산 연결 | 단계와 실제 입출력·장 전달·반복의 관계 | 선택 단계의 연결·단위·반복 설정과 실제 단계 결과. 물리 모델 값은 원 도구에서 편집한다. |
| Runner — 실행 관리 | 정렬 가능한 작업표와 작업/실행 명령 | 선택 작업의 실제 진행·로그·입력·결과. 상태에 맞는 중단·원 입력 열기·결과 열기·새 실행을 제공한다. |
| Expert — 전문가 토론 | 논점·대화·자료 탐색, 발언 답글·자료 추가·인용·계획 명령 | 다자 발언과 사용자 입력, 선택 인용의 원 자료. 제안은 편집할 수 있는 수치 계획으로 넘기고 실제 결과를 같은 논의로 가져온다. |
| Study — 연구 노트 | 연구 질문·가설·근거 탐색, 비교·판단·다음 연구 명령 | 선택한 표·곡선·결과 비교와 그 질문의 판단·이유. 수치 계획 편집기나 긴 보고서로 대체하지 않는다. |
| Report — 보고서 | 절·그림·표 목록과 출력/내보내기 명령 | 실제 출력 페이지. 저장된 결과의 표·곡선·장면과 판단을 구성한다. 문서 형식은 이 도구의 목적에 맞게 사용한다. |
| Workbench — 연결 보기 | 기존 모델·자료·계산·결과의 관계와 원 도구 열기 | 연결도 또는 관계표에서 선택 관계를 따라간다. 다른 도구를 쓰기 위한 필수 관문이 아니다. |

메뉴·아이콘은 실제 명령을 나타내고, 트리는 실제 대상 관계를 나타낸다. 확대·맞춤·범위·선택·
성분·시간 명령은 해당 뷰 가까이에 둔다. 도구 막대는 같은 명령의 활성 상태와 단축키를 공유한다.
공통으로 맞출 것은 이름·선택·초점·편집·저장·창의 동작이며, 모든 앱에 같은 카드/폼 배치를 강제하지 않는다.

Data의 취득 기능은 채널·시간 신호·연결 상태를 다루는 별도 작업창으로 둔다. 워크시트에
장비 설정을 늘어놓지 않으며, 실제 장비가 없어도 파일 자료 분석을 사용할 수 있다.

Material 안에서 쓰는 Numerical 계획 편집기와 독립 Numerical은 같은 계획·편집 부품을 쓴다.
LabPlot을 채택하면 본격적인 원자료 편집은 독립 Data 창에서 한다. Material에는 필요한 자료
보기와 ‘원자료 편집’을 두고 같은 문서를 연다. 다른 런타임의 창을 이미 임베딩했다고 설명하지 않는다.

OpenScience는 Expert가 실제 허용된 모델·검색·도구를 쓰는 연결 계층이다. 별도 구독 버튼이나
연구 문서를 하나 더 만드는 화면이 아니다. 실제 연결이 없으면 그 상태를 표시하고, 독립적인
자료·계산·로컬 기록 작업은 계속 사용할 수 있게 한다.

## 3. 실제 기반의 선정 범위

아래 경로는 Pro가 선정하고 Astra가 수용한 개발 복구 방향이다.
LabPlot은 먼저 실행 가능한 한정 뼈대에서 판정한다. 아직 제품에 도입되거나 사용자에게
채택 승인된 상태가 아니며, Data만 C++/Qt/KDE로 바꾸는 영향도 이 판정에 포함한다.

| 기반 | 그대로 사용할 부분 | 새로 연결하거나 판단할 부분 |
|---|---|---|
| FreeCAD | CAD/FEM 객체·모델 트리·선택·Tasks·파일 편집과 기존 Lab workbench | 기존 adapter·입력 생성·실행·결과 복귀를 같은 실제 사용자 모델에서 마무리한다. |
| ParaView | reader·pipeline·필터·3D/표/차트·시간·선택 | 기존 bridge·측정·분석·문서 연결을 유지한다. 별도 Qt 3D 후처리기를 만들지 않는다. |
| LabPlot | 프로젝트 탐색·워크북·표·곡선·속성·내부 QADS 도킹과 활성 객체 명령이 연결된 실제 Data 작업 환경 | 앱 포크/확장에서 기존 Data 문서를 잇는 첫 한정 뼈대를 확인한다. Python 위젯 이식으로 설명하지 않는다. |
| 나머지 Research의 PySide6 | 기존 계산·reader·문서 명령과 유효한 Matplotlib 조작 | 긴 폼 조립 화면층은 앱별 작업면으로 교체한다. 공통 QMainWindow/QDockWidget·명령·선택 구조를 사용하며 LabPlot 내부 의존성을 자동 추가하지 않는다. |
| FEBioStudio·PrePoMax | 이번에는 FE 작업 관례 참고 | FE 문서·실행 체계를 하나 더 의무화할 이득이 부족해 host·소스 이식은 선택하지 않는다. C++/C#이라는 언어가 제외 이유는 아니다. |
| SMTK/CMB·SALOME | resource/operation 또는 module/study/selection/view 비교 자료 | 이번에는 플랫폼 이관을 선택하지 않는다. 현재 Core와 모델·명령 소유를 중복시키는 범위가 GUI 복구보다 크다. |
| OpenCADStudio | 공개 CAD 앱 구조 비교 자료 | 기존 native CAD를 유지하면서 CAD 중심 저장·편집을 다시 개조할 범위가 커 이번 기반으로 선택하지 않는다. |

공식 소스: [LabPlot](https://github.com/KDE/labplot),
[FEBioStudio](https://github.com/febiosoftware/FEBioStudio),
[PrePoMax](https://gitlab.com/MatejB/PrePoMax), [SMTK](https://github.com/Kitware/SMTK),
[SALOME GUI](https://github.com/SalomePlatform/gui).
WELSIM과 상용 공학 앱은 작업 배치·조작 참고이며 본체 소스·브랜드·아이콘을 복제하지 않는다.
ada-py의 기존 조사는 필요한 reader/writer 카드가 있을 때 이어간다.
LabPlot의 실제 재사용 부품은 `MainWin`, `ProjectExplorer`, `GuiObserver`, `ActionsManager`,
`AbstractAspect/AbstractPart`, `ContentDockWidget`과 Spreadsheet·Worksheet·곡선 편집이다.
[선택과 작업창 활성화](https://github.com/KDE/labplot/blob/ffd1eb53fcd5d033810af092a255b25cab7c93d1/src/frontend/MainWin.cpp),
[속성 공급](https://github.com/KDE/labplot/blob/ffd1eb53fcd5d033810af092a255b25cab7c93d1/src/frontend/GuiObserver.cpp)을
남기는 앱 수준의 차용이다. 창 테두리만 남기고 기존 폼을 다시 넣는 방식은 선택하지 않는다.

## 4. 실제 뼈대와 첫 제품 인도를 구분한다

### Research 기반을 결정할 한정된 뼈대

가져온 앱의 실제 탐색·표·곡선·속성·메뉴·명령·도킹을 유지하면서, 기존 Core의 Data 문서 한 개와
공개 시험 자료 두 개를 연결한다. 가져오는 원본 부품, 새 adapter, 자료 편집·보기 편집·Undo·저장의
담당을 먼저 명시한다. 두 저장소의 값과 편집 이력이 조용히 갈라지면 통합 성공이 아니다.

확인할 작업은 열/단위가 있는 표 열기, 같은 행·곡선·범위 선택, 기존에 지원하는 열 대응·단위·
배율·제외 구간 편집, 되돌리기, 같은 원자료로 저장·재열기, 정확한 자료를 Material로 전달하기다.
중복 좌표·정렬·필터 뒤에도 선택한 원행이 바뀌지 않아야 한다. 가짜 Core나 고정
그래프를 사용하지 않는다. panel 이동·복원, 활성 뷰, 한국어·단위·키보드도 같은 앱에서 확인한다.
CSV를 한 번 여는 장면이나 클릭할 수 없는 껍데기로 마감하지 않는다.

### 공통 요소의 실제 연결

| 요소 | 뼈대에서 작동해야 할 동작 | 소유와 기존 연결 |
|---|---|---|
| 명령 | 메뉴·도구 모음·문맥 메뉴·단축키가 같은 명령과 활성 조건을 사용한다. 실행할 수 없는 이유는 선택 대상에서 확인한다. | 각 앱의 명령을 GUI 담당이 연결하고 공통 dispatch 변경은 Codex가 맡는다. |
| 현재 선택 | 탐색기·표·곡선·설정이 같은 대상을 가리킨다. 정렬·필터 후에도 화면 행 번호를 원자료 행 번호로 쓰지 않는다. | donor의 실제 선택 모델과 기존 Data 원자료 대응을 adapter가 잇는다. 원행 대응은 아직 구현 확인이 필요하다. |
| 편집·되돌리기 | LabPlot의 현재 편집 버퍼·Undo와 Core의 적용된 입력·저장을 구분한다. Apply/Save 뒤 Undo도 로컬 버퍼의 새 미적용 변경이다. | 같은 Ctrl+Z/Redo가 Core Undo까지 겹쳐 호출하지 않는다. 다음 적용은 마지막 확인 세대에 대한 기존 `data.update` 한 건이다. 나머지 PySide6 앱의 기존 문서 Undo를 일괄 교체하지 않는다. |
| 저장·복구 | 미저장 편집, 외부 변경 충돌, 실패한 저장을 구분하고 원 문서와 현재 편집을 보존한다. 재열기 결과로 연결 여부를 확인한다. | 기존 문서 명령·결과·참조 API를 사용한다. 새 프로젝트 저장 서비스는 만들지 않는다. |
| 뷰·도킹 | 활성 표/그래프 전환, 확대·맞춤·선택, 패널 이동·닫기·복원과 창 배치가 실제로 작동한다. | donor의 부품을 유지한다. 다른 PySide6 앱에 LabPlot 전체나 그 내부 도킹 의존성을 자동 전파하지 않는다. |
| 공통 외관 | 짧은 명령명, 역할이 분명한 아이콘, 한글·수치·단위, 초점·선택 표시와 간격을 일관되게 적용한다. | PySide6는 기존 `appearance.py`를 재사용한다. C++ donor에는 같은 시각 규칙을 해당 Qt 코드로 대응한다. Python 모듈을 그대로 import하는 관계가 아니다. 아이콘의 사용 조건도 확인한다. |

LabPlot은 Python 위젯이 아니다. 기존 `apps/lab/server.py`·`workbench_routes.py`의 로컬 API와
`caelab/workbench_client.py`의 실제 호출을 기준으로, C++ 쪽에 한정된 연결 코드를 작성해야 한다.
일반 문서 편집·Undo·저장은 `document_command`, 처리·취득 등의 전용 동작은 기존
`DataMaterialService`가 담당한다. 새 웹 화면·외부 서버·별도 저장 체계를 추가하지 않는다.
이 연결이 작동한다고 확인한 것은 아니며, 이것이 다음 뼈대의 구현 대상이다.

기존 미리보기 API가 전체 워크시트를 이미 공급한다고 가정하지 않는다. `document_source_preview`와
입력 미리보기는 제한된 텍스트/행 미리보기이며 전체 CSV·NPZ 자료 경로가 아니다. 먼저 기존
reader·owner에서 정확한 전체 원자료와 원행을 읽는 경로를 연결한다. 필요한 transport가 없다면
Codex가 그 위에 좁은 읽기 전용 API를 추가한다. 별도 parser·서버·자료 저장 계층은 만들지 않는다.
따라서 신규 범위는 C++ 연결 코드만으로 단정하지 않고, 이 읽기 연결과 필요한 API 확장까지 포함한다.

자료 설정의 적용과 계산된 자료의 전달도 구분한다. `data.update`는 초안과 세대를 바꾸며,
실제 자료 배열·보존 결과는 기존 `data.import` 또는 해당 processing 명령이 만든다. 다른
도구에서 사용하려면 현재 설정과 일치하는 실제 결과를 확보하고 정확한 보존 결과 참조로
전달한다. 이전 import 결과를 새 설정의 결과로 넘기지 않는다. 저장·Undo·행 선택·재열기만으로
import나 solver·AI를 자동 호출하지 않는다. 기존 결과와 다른 현재 편집은 화면에서 구별한다.

Core가 다른 창·Python·CLI에서 바뀌면 오래된 버퍼로 덮지 않고 그 버퍼를 보존한 채 충돌
복구로 전환한다. donor의 편집 버퍼는 제출 전까지 현재 창의 편집본이며, 적용과 저장이 모두
확인되기 전 전체 저장 완료로 표시하지 않는다. LabPlot 작업 파일은 보기·배치·편집 복구와 Core 연결을
보조한다. 원 공학 문서나 원자료를 대체하는 새 저장 형식으로 만들지 않는다.

### Data 편집·전달·부분 저장의 계약

| 사용자 행동 | 확정한 동작 |
|---|---|
| 열 대응·단위·배율/오프셋·제외 편집 | 원자료 값은 보존하고 로컬 버퍼를 바꾼다. 단위 이름을 바꾸는 것과 수치를 변환하는 것을 구분한다. |
| Ctrl+Z/Redo | 항상 현재 donor 버퍼만 바꾼다. 적용·저장 뒤에도 새 미적용 편집이 되며 마지막 Core 적용본과 다른 앱의 결과는 그대로다. 적용할 때마다 이력을 지우지 않는다. 재열기 후 이전 프로세스의 Undo 이력이 그대로 복원된다고 약속하지 않는다. |
| 적용 | 마지막 확인 session/generation에 대해 전체 draft를 `data.update` 한 건으로 제출하고 확인 응답을 새 적용 기준으로 삼는다. `QUndoStack.isClean()`만으로 적용·자료 저장·보기 저장을 합쳐 판단하지 않는다. |
| 저장 | 필요하면 버퍼 적용→Core 저장 확인→정확한 Core 저장 참조를 포함한 donor 파일의 임시 기록·최종 교체 순서다. 자료 저장과 보기 저장을 구분한다. |
| Material/Numerical에서 사용 | 현재 입력과 일치하는 실제 import/processing 결과가 있으면 재사용한다. 없으면 사용자가 요청한 자료 준비에서 기존 명령을 실행한 뒤 정확한 보존 결과 참조로 넘긴다. 단순 `data.update` 응답을 배열 생성 완료로 취급하지 않는다. |

적용·저장 중에는 해당 문서의 공학 편집과 Undo를 직렬화한다. 요청에 고정한 문서·입력의
응답만 반영하고 다른 문서를 연 뒤 도착한 응답으로 현재 창을 바꾸지 않는다. 응답이 유실되면
같은 명령을 확인·재시도한다. session이 바뀌었거나 결과가 불명확하면 재읽기·복구로 전환하며,
새 명령 ID와 generation으로 무조건 재전송하지 않는다. 외부 입력으로 버퍼를 다시 읽을 때
이전 입력의 로컬 공학 Undo를 재사용하지 않는다. 입력 충돌과 단순 결과/저장 상태 갱신도 구분한다.

| 실패한 단계 | 보존·표시·재시도 |
|---|---|
| 적용 실패 | 편집 버퍼와 기존 Core 적용/저장본을 보존한다. 입력 오류·충돌·응답 유실을 구분한다. |
| 적용 성공, Core 저장 실패 | 적용된 작업 입력과 이전 saved revision을 보존한다. Core 저장 단계만 확인·재시도하며 정상 donor 파일을 새 저장본과 연결됐다고 교체하지 않는다. |
| Core 저장 성공, 보기 저장 실패 | 새 Core revision과 이전 donor 파일을 모두 보존한다. ‘자료 저장됨 / 보기 저장 실패’를 표시하고 같은 참조로 보기 저장만 재시도한다. Core를 되돌리거나 불필요한 새 revision을 만들지 않는다. |
| 양쪽 저장 성공 | 정확한 Core 저장 참조를 담은 donor 파일을 최종 교체한 뒤 전체 저장 완료로 표시한다. donor의 조기 dirty 해제 동작은 보완한다. |

재시도는 고정한 저장 스냅샷에 묶는다. 새 편집을 시작한 뒤 오래된 저장 응답으로 덮지 않는다.
재열기 때 donor 파일의 기준과 Core가 다르면 확인·복구하며 자동 적용하지 않는다. Core 연결이
없으면 가능한 캐시 보기를 명시하고 적용·저장 성공이나 다른 도구 전달을 주장하지 않는다.

원행은 원자료·열 신원과 `source_row_kind`·`source_rows`로 대응한다. CSV/TSV는 0부터 세는
실제 텍스트 줄, NPZ는 배열 인덱스이며 include/exclude 범위는 양 끝을 포함한다. 정렬은 연결
열 전체의 보기 순열로 처리한다. 중복 x값·표시 점 축소 후의 점 번호나 화면 행 번호를 원행으로
보내지 않는다. 표시 정렬 때문에 계산 입력을 정렬·중복 제거하지 않는다. 현 reader의 단조 축
제약을 위반하는 자료도 편집·표시는 가능하지만 유효한 선택 없이 import 성공으로 만들지 않는다.
계산 제외·품질 표시·화면 숨김은 각각 유지하며 donor mask 하나로 합치지 않는다.

이 확인으로 LabPlot Data 앱 도입 여부를 결정한다. 원본의 핵심 동작을 거의 다 버려야 하거나
자료 의미를 보존할 수 없고 Core를 광범위하게 다시 써야 하면 전체 fork 경로를 탈락시킨다.
이때 대안은 Data도 나머지 연구 앱과 같은 PySide6 작업면 교체로 합치는 것이다. 같은 후보
목록과 정적 그림을 반복하는 새 연구 과제로 늘리지 않는다.
Windows에서 추가 지출 없는 빌드·실행 경로와 포함 부품의 배포 조건도 같은 확인의 판정에
넣는다. 소스를 읽었다는 사실만으로 빌드·실행·배포가 된다고 표시하지 않는다.

### 첫 제품 인도 — native 모델을 고쳐 결과 비교

기존 지원 경로에서 지그 기준안과 변경안의 FreeCAD 편집→입력 생성→Runner 계산→ParaView
비교→원 설계 복귀를 완결한다. 같은 원 입력·성분·단위·시각의 결과를 구별하고, 실패한 입력은
원 편집기로 돌아가 수정한다. 저장 후 다시 열 때 재계산하지 않고 두 결과와 원 모델을 이어 쓴다.
새 접촉 법칙이나 새 solver 전체를 이 인도의 선행조건으로 넣지 않는다.

대상은 기존 공개 지그 모델과 FreeCAD–CalculiX 지원 정적 해석이다. 임의의 단순 블록을
새로 만들어 대체하지 않는다. native Tasks의 취소와 수락을 실제 입력으로 확인한 뒤 기준안과
치수 또는 조건 한 항목을 바꾼 변경안을 계산한다. 메시가 달라졌을 때 미지원 절점별 차분을
만들지 않고, 같은 물리량·성분·단위·하중 상태의 나란히 보기와 정의된 응답을 비교한다.

### 병렬 Research 인도 — 두 시험에서 재료 후보 채택

Data→Material→기존 Numerical 동정/별도 확인→선택 후보 비교→원 Material 채택·재개를
완결한다. 자료의 품질 제외와 계산의 동정/확인 용도를 구분하고, 후보 보기만으로 원 계수를
바꾸지 않는다. 이 인도를 모든 CAD/FE·Post 작업의 선행 관문으로 만들지 않는다.

## 5. 코드와 담당의 경계

| Pro | 전체 제품·기반·중요 설계 판단 | 작은 문구 교정마다 새 대화를 만들지 않는다. |
| Astra Extra High | 의미 있는 통합 결과의 독립 검토 | 원 요구·실제 코드·실제 창과 사용자 작업을 함께 검토한다. |

기존 reader·수치 엔진·JobManager·문서별 owner와 저장한 입력/결과는 기본적으로 보존한다.
재귀적으로 저장 속성을 펼치는 폼, 다른 앱의 화면을 상속해 의미를 섞는 구성, 교정이 여러 번
누적된 재배치는 새 작업면으로 교체한다. 동작과 무관한 전체 폴더 이동이나 수치 엔진 재작성은
GUI 복구의 선행조건으로 만들지 않는다.

각 담당은 맡은 전용 파일에서 기능·화면·필요 검사·사용법까지 끝낸다. 공통 Core 파일 변경은
Codex가 적용한다. 마지막에 처음 만나 병합하는 방식 대신 첫 원 문서/선택/명령이 연결되는
시점에 통합한다. 일반 교정은 묶어 처리하고 Pro/Astra의 전체 검토를 매번 새로 열지 않는다.

현재 표는 구현 재개 때의 책임 배분이다. 이미 여러 구현 에이전트가 개발 중이라는 보고가
아니다. 공통 UI 파일은 같은 데스크톱 담당 한 명이 쓰고, 공통 Core·API·dispatch는 Codex가
쓴다. 기능별 폴더 배치는 [코드 경계](CODE_STRUCTURE.md)를 따르되 실제 기능 변경과 함께
옮긴다. 빈 폴더와 범용 폼 framework를 먼저 늘리지 않는다.

MoAI는 기존 SPEC·todo·중요 결정·통합·문서 동기화에 사용하는 도구다. 실제 제공된 MCP/CLI를
확인해 쓰고, 작성과 직접 대화는 실제 Codex 에이전트와 별도 Pro 연결이 수행한다. ponytail은
이미 완성된 코드와 도구를 적극 재사용해 요청한 작업을 적은 새 코드로 끝내는 기준으로 쓴다.
별도 전처리·후처리·수치 엔진을 다시 만드는 것으로 과제를 바꾸지 않는다. 기존 업무에서
끝나지 않는 연결과 화면만 고치며, 저장·재개를 매번 별개의 새 기능으로 세지 않는다.

## 6. 새 세션과 비용·인수 범위

최종 방법과 첫 작업을 확정한 뒤 새 Codex 세션에 같은 저장소를 인계하는 것을 권고한다.
새 세션 자체가 품질을 보장하지 않는다. [CODEX_START](../CODEX_START.txt)는 현재 역할과
실제 뼈대 확인의 원칙을 반영했고, 오래된 W1–W5·승인 대기·모델 기본값 충돌을 정리했다.
새 세션/Goal/자동화를 자동 생성하지 않는다. 현재 배정과 다음 행동은 CURRENT_STATE만 따른다.
새 세션에 같은 전체 진단을 다시 시킨 뒤 보고만 하고 멈추는 관문은 추가하지 않는다. 확정된
기반·파일 소유·첫 종료 장면을 인계하고, 사용자가 구현을 재개하면 배정 범위의 실제 뼈대와
native/Research 인도를 일상 재승인 없이 진행한다.

추가 지출은 0원이다. 현재 조사에서 소스·SDK·새 라이브러리를 제품에 반입하지 않았다.
LabPlot의 GPL, FEBioStudio의 MIT 등 각 원본과 하위 부품의 LICENSE/NOTICE를 실제 반입 파일과
배포 방식에 맞춰 확인한다. 공개 저장소라는 이유로 모든 코드·아이콘을 자유롭게 복제한다고
가정하지 않으며, 비용이 필요한 조합은 선택하지 않는다.

이번 작업에서 새 solver·native 앱·장비·AI 제품 연결을 실행하지 않았다. 프로그램 실행,
GUI 사용성, 수치 검증과 공학적 적합성은 각각 확인한 범위대로 기록한다. 기존 실패와 UNKNOWN,
원래 허용치는 보존한다. 테스트로 연 프로그램은 자기 PID/자식만 추적해 성공·실패·시간 초과
모두 정리하며, 사용자 창은 종료하지 않는다.

## 7. 검토 결과와 다음 판정

Pro는 기존 GUI 보수의 우위를 미리 확정했던 첫 결론을 철회하고, 완성형 Data 환경 차용과
앱별 화면층 교체를 선택했다. Astra는 이 선택·native 첫 인도·Research 병행을 수용했다.
Codex는 Astra가 실제 API에서 확인한 전체 표 읽기 부족, `data.update`와 자료 생성의 차이,
로컬 Undo·부분 저장·원행 계약을 위에 통합했다. Pro가 이 보완본을 다시 작성했다거나 제품을
실행했다는 뜻은 아니다. 반려된 네 정적 시안은 공개 승인본으로 게시하지 않는다.

현재 설계 방법의 미결 쟁점은 닫았다. 남은 판정은 정해 둔 한정된 실행에서 **LabPlot을 Data에
실제로 채택할 수 있는가**이며, 결과에 따른 대안도 위에 정했다. 전체 기능·지원 조합·종료식은
기존 [DEVELOPMENT_ITEMS](DEVELOPMENT_ITEMS.md)를 유지한다. 이번 첫 뼈대나 첫 지그가 전체
제품 완료를 대신하지 않는다. 이번에 제품 기능의 완료 상태를 올리거나 GUI 수용을 선언하지 않았다.

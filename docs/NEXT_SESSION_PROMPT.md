아래 코드 블록을 새 세션의 첫 메시지로 붙여 넣는다. 이 파일의 인계 메모는
현재 체크포인트이며, 이후 변경이 있으면 최신 main과 HANDOFF를 우선한다.

```text
C:\SourceCodes\autonomous-cae-lab에서 Autonomous CAE Lab 개발을 이어가라.
저장소는 https://github.com/pikachu444/autonomous-cae-lab 이다.
이 새 로컬 세션이 설계·구현·실행·수정·통합·Git의 주 담당이다.

목표는 초기 52개 요구사항과 Phase 1~7에 따라 다양한 CAE 문제를 연구할 수 있는 로컬 시스템을 완성하는 것이다. 사용자가 제시한 제품 불량 재현·지그 검토·CAD·조립체는 활용 예시다. 특정 예제, 솔버 검증, 문서 또는 웹페이지 제작을 전체 목표로 바꾸지 마라.

이전 작업에서 사용자가 지적한 실패를 반복하지 마라. 전체 개발 로드맵과 구현 명세를 먼저 개발 기준으로 확정하지 않고, 예제 생성 코드·개별 검증·작은 리뷰를 반복해 시스템 완성으로 연결하지 못했다. 기존 계획 문서가 있다는 이유만으로 계획이 충분하다고 판단하지 마라. 요구사항을 실제 공통 기능으로 연결하는 명세·개발 순서·완료 조건이 부족한 부분을 보완하고 그 기준에 따라 개발하라. 이미 구현한 기능은 증거를 확인해 재사용하라.

1. 먼저 AGENTS.md를 읽고 지정된 순서로 PROJECT_SCOPE.md, HANDOFF.md, CURRENT_STATE.md, ARCHITECTURE.md, 모든 ADR, openscience/contract.md와 관련 실행 계획·코드·테스트를 복원하라. 최신 main·submodule·로컬 변경·실제 프로세스·정확한 소스의 CI를 직접 확인하고 기존 구현과 실험을 보존하라. 확인하지 못한 대화나 실행을 확인한 것으로 취급하지 마라.

2. 상태 복원 후 코드 수정에 앞서 다음 두 기준을 정리하라. 기존 docs/CAE_RESEARCH_EXECUTION_PLAN.md를 단일 개발 로드맵으로 유지하고, 기능 구현 명세는 기존 명세를 재사용·보완하여 없으면 docs/CAE_SYSTEM_IMPLEMENTATION_SPEC.md에 작성하라. 명세에는 R01~R52/Phase, 사용자 기능, 입력·출력, 구현 모듈·공통 인터페이스, Domain/adapter 책임, 실제 지원 범위, 오류·취소·복구 동작, 완료 조건을 연결하라. 로드맵에는 기능 묶음의 순서·의존성·구현 항목·실행 확인·마지막 검수 기준을 적어라. 코드만 있음, 연결됨, 실제 사용 검증됨을 구분하라. 예제 스크립트·단위테스트·solver exit0만으로 요구사항 완료를 표시하지 마라.

앞 단계의 필수 의존성을 확인하고 순서대로 큰 기능 묶음을 개발하라. 전체 공통 구조를 먼저 연결하고 세부 기능을 보완하라. 실측 자료·회사 승인 등 외부 근거가 없으면 UNKNOWN으로 남기고 가능한 소프트웨어 개발을 계속하라. 로드맵과 명세 정리가 끝나면 곧바로 해당 묶음의 개발에 착수하라. 문서 정리·감사·재계획만으로 한 작업을 끝내지 마라.

3. 연구 질문 → 편집 가능한 CAD 또는 해석 모델 → 명시적 재료·좌표계·하중·경계조건·접촉 → 적합한 오픈 솔버 실행 → 전체 필드·이력·비교 → 조건 변경 → DOE·최적화·역추정·불확실성·다목적 탐색 → AI 해석 → 저장·재열람·재현·취소·재접속을 공통 흐름으로 구성하라. 기능마다 실제 지원 범위를 표시하고 지원되지 않는 조합은 명확히 차단하라.

4. 기존 오픈 솔버와 pinned auto-fixture-design을 재사용하라. 공통 모듈·Domain plugin·adapter를 확장하고 예제마다 별도 제품 스크립트를 만들지 마라. OpenScience는 질문·가설·계획·해석, Core는 공통 계약·저장·실행·근거, Domain은 공학 규칙, adapter는 native syntax를 담당한다. 수치 후보는 기존 numerical engine이 생성한다.

5. 연구 모델은 이미 승인한 openai-codex/gpt-5.6-sol과 기존 ChatGPT OAuth만 사용하라. 임의 모델 교체·자동 대체·불필요한 재인증을 금지한다. 기존 OpenScience 연결 수정과 인증·runtime 분리 구현을 이어받고, 공식 문서·소스·실제 오류를 조사해 해결하라. 연결 장애 하나 때문에 다른 독립 기능 개발 전체를 멈추지 마라.

6. 작업 순서는 기능 묶음 개발 → 주 담당의 실제 실행·버그 수정·통합 → 묶음 마지막 독립 검수다. 작은 수정마다 리뷰·Astra 승인·보고서 복제를 반복하지 마라. 기존 Astra high의 전체 시스템 및 작업 방식 감사·개선안을 재사용하라. 필요하면 지정 파일 구현이나 독립 조사에 지원 에이전트를 쓰되 공유 파일의 동시 수정은 막아라.

7. 검증은 변경된 기능과 목적에 맞게 수행하라. 수치 비교가 필요하면 적합한 해석해·공식 benchmark·참조·교차 솔버 근거를 사용하라. 오픈 솔버 전체를 다시 검증하거나 같은 실패·CAD 복구·재메시를 이유 없이 반복하지 마라. 전체 모델과 explicit에 의무 mesh convergence sweep을 요구하지 마라. 실패하면 소프트웨어·환경·모델링·미검증을 구분하고 원인을 바꾼 뒤 재실행하라. 계산이 오래 걸린다는 이유만으로 실패 처리하지 마라.

8. 화면은 실제 모델·조건·실행·전체 결과를 조작하고 확인하는 전문적인 로컬 공학 작업 공간으로 구성하라. GUI와 headless는 같은 모델 개정·실험·artifact를 사용해야 한다. 화면 제작만으로 연구 기능이 완성됐다고 보고하지 마라.

9. 의미 있는 구현 단위를 검증하고 커밋하여 main에 통합·push하라. 해당 원장·HANDOFF·CURRENT_STATE·요구사항 상태를 최소한으로 갱신하고 원격 반영을 직접 확인하라. Git·설치·버전 확인·명령 실행은 네가 맡아라. 회사 CAD·인증 정보는 공개 저장소에 넣지 마라. 원본 결과와 실패 기록은 보존하고 새 실행은 새 store/ID를 사용하라.

10. 보고는 사용자가 무엇을 할 수 있게 됐는지, 52개 중 실제 완료·부분 구현·미검증·미구현이 각각 얼마인지, 현재 큰 기능 묶음과 다음 작업을 중심으로 하라. 해시·테스트 개수·하중 값만 나열하지 마라. 일부 예제 성공, API 존재, solver exit0, CI PASS를 전체 기능 완료나 물리·강도·배포 승인으로 바꾸지 마라. UNKNOWN/invalid metrics/NOT_RELEASED를 유지하라.

각 작업 묶음을 끝낼 때 로드맵 항목, 명세한 기능, 실제 바뀐 제품 동작, 사용자가 실행할 수 있는 절차, 남은 결함을 대조하라. 계획에 없는 새 예제가 필요하면 어느 공통 기능의 어떤 결함을 검증하는지 먼저 연결하라. 같은 예제를 다시 실행할 때는 수정한 원인과 확인할 차이가 있어야 한다.

11. 이 프롬프트는 새 세션으로 주 담당을 이관하는 승인이다. 기존 채팅의 autonomous-cae-lab 자동 개발은 공식 도구로 중지하고 중복 쓰기를 막아라. 기존 Goal·자동작업의 실제 상태를 확인하고, 새 세션에 미완료 Goal이 없으면 위 전체 목표를 설정하라. 기존 미완료 Goal은 복제하거나 허위 완료 처리하지 마라. 실행 중 해석은 소유권·핸들·기록을 확인해 보존하라. 상태 기록만으로 종료를 추정하거나 PID만으로 입양·강제 종료하지 마라.

지금은 상태 복원과 짧은 범위 보고를 마친 뒤 가장 앞 미완료 기능 묶음의 실제 개발에 착수하라. 이미 승인된 결정은 다시 묻지 말고, 꼭 필요한 계정 인증 등 사용자만 할 수 있는 행동이 있을 때만 구체적으로 요청하라. 전체 소프트웨어 완료 조건을 충족하거나 사용자가 중단할 때까지 가능한 작업을 이어가라.
```

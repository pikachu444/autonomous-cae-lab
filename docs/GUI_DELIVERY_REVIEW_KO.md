# GUI와 개발 인도 실패 진단

2026-10-18. 사용자 요청으로 GPT-6 Astra/xhigh와 새 실제 ChatGPT Pro 대화가 각각
독립 진단했다. 진단 대상은 `7847c33`의 관련 코드·요구/운영 문서와 기존 제출 화면이다.
두 쪽이 먼저 자기 결론을 냈고 Codex가 관련 소스와 대조했다. 이번 작업은 진단이며
제품 코드 수정이나 새 GUI 제작을 수행하지 않았다.

## 결론

전체 CAE 연구 도구군은 큰 개발 과제다. 그러나 읽기 쉬운 이름, 익숙한 메뉴와 선택,
자료·모델·결과 중심 화면, 일관된 저장·취소를 요구한 것은 통상적인 제품 요구다.
기술적 난도를 낮은 기본 완성도의 설명으로 삼을 수 없다.

두 진단의 공통 결론은 **이미 구체화된 사용자 지시를 실제 구현의 선택 기준과
미달 산출물의 반려 기준으로 적용하지 못했다**는 것이다. 원래 요구가 모호했다거나
Qt로는 전문 화면을 만들 수 없었다고 볼 근거가 없다. 공통 테마와 실제 서비스 기반은
있으며, '아무 설계가 없다', '기본 Qt 그대로다', '원래 못한다'는 단정도 진단을 흐린다.

## 확인한 원인

| 원인 | 실제 사례와 영향 |
|---|---|
| 사용자 작업보다 내부 설정 구조를 화면에 옮김 | PDE의 `_add_fields`는 dict/list를 재귀적으로 입력칸으로 만든다. Numerical에는 원시 타입 편집 경로가 있고 Material은 시험 선택보다 전체 F 이력 편집이 주 화면을 차지한다. 항목을 더할 때마다 폼·탭·설명이 늘어나기 쉽다. 필요한 전문 입력을 없애라는 뜻은 아니다. |
| 개별 확인을 사용자 인도로 마감하지 못함 | 코드 통합과 한정 검사를 마쳐도 실제 자료 열기부터 결과 비교·저장·재개까지의 업무가 남았다. PRODUCT_PLAN §7에는 제한된 Material 인계를 전체 기획 준비로 보고한 Root 판단을 철회한 기록이 있다. |
| 병렬 작성과 전체 업무 완결 사이의 책임을 닫지 못함 | 파일별 작성·검토·통합은 있었지만 창 이동, 선택, 저장과 복구의 연결을 뒤로 미루는 부담이 Codex 통합 단계에 모였다. 실제 대기시간 중 Pro/검토가 차지한 비율은 이번 자료로 산정하지 않았다. |
| 같은 기능을 앱마다 다른 방식으로 조작 | 편집 Undo와 계산 취소에 같은 '실행 취소' 이름을 쓰고, 적용·저장·닫기 동작도 앱마다 다르다. 작업 사본을 만든 뒤 GUI로 열기보다 `--store` 실행을 안내하는 코드도 남아 있다. |
| 현재 지시·기록·설명이 불일치 | CURRENT_STATE 상단의 자동 재개 금지와 하단의 일곱 인도 병렬 작성이 충돌했다. 옛 화면과 현재 코드를 섞어 설명하거나 Study와 Numerical을 혼동한 설명도 문제였다. 이 충돌은 최신 지시를 어긴 데 대한 면책이 아니다. |

색·폰트만 바꿔도 같은 문제가 반복되는 이유는 작업 대상과 명령의 배치가 그대로이기
때문이다. Post의 최초 UI 생성 뒤 두 차례 재배치와 숨긴 버튼에 연결하는 명령처럼,
교정이 기존 구조 위에 누적되는 코드도 Pro가 지적했다.

## Codex가 확인한 범위와 보정

- `appearance.py`에는 실제 공통 스타일·팔레트·글꼴·선택/포커스 처리가 있다.
- `pde_window.py`의 재귀 폼, `runner_window.py`의 계산 취소와 편집 Undo의 동명 표시,
  `connection_window.py`의 사본 저장 후 `--store` 안내를 소스에서 확인했다.
- 제출된 Data 사진에서는 가져오기 설정이 크지만, 현재 `_opened`는 runs가 있는 문서에서
  설정을 접는다. 이 부분을 현재 모든 상태에 남은 결함이라고 일반화하지 않는다.
- FreeCAD의 전문적인 기본 화면은 기존 제품 재사용이다. 제출된 ParaView 렌더는 전체
  OS 창이 아니다. 빈 Runner와 미전송 Expert 초안은 그 상태의 사진이지 전체 작업 완료나
  AI 답변 품질의 근거가 아니다.

검토자는 문서와 관련 코드, 원본 이미지 14개를 읽었다. 새 Windows 직접 조작, 전체
제품 실행, 솔버 캠페인과 공학적 적합성 검증은 하지 않았다. Pro에게 제공되지 않은 일부
보조 모듈과 전체 과거 대화의 판단을 전수 검토했다고 주장하지 않는다. 모델의 불변 능력,
내부 라우팅이나 악의적 토큰 낭비를 확정할 근거도 없다.

## 유지·교정·중단 권고

**유지:** FreeCAD/ParaView의 native 기능, 기존 수치 엔진·reader·JobManager·문서 owner,
단위와 물리적 의미, 원자료와 이전 결과 보존. 전면 재작성·새 언어 전환이 필수라는
결론은 아니다.

**교정:** 사용자가 열·시험·영역/경계·후보·판단을 선택하면 관련 편집과 결과가 함께
바뀌도록 화면을 구성한다. 앱 사이 저장·Undo·계산 취소·열기의 의미를 일치시킨다.
지원하는 기능의 정상·편집·실패·복구 상태를 같은 실제 작업에서 확인한다.
Runner의 첫 행동을 개선할 수 있으며, 별도 새 런처 앱은 아직 채택한 해법이 아니다.

**중단:** 문구·색상 변경을 전체 GUI 개선으로 보고하기, 작은 수정마다 새 Pro/전체 리뷰를
열기, 파일 작성·검사 수·스킬 이름을 사용 완료로 대신하기, GUI 때문에 변경하지 않은
솔버를 반복 검증하기, 폴더 전체 이관을 제품 인도의 선행조건으로 삼기.

## 검토자들이 제안한 다음 인도

두 쪽 모두 두 시험파일에서 자료 처리→재료 평가→후보 비교→계수 채택→종료 후 재개를
끝내는 하나의 Research 업무를 권고했다. Pro는 같은 작업의 Study 판단과 Report 출력까지
포함했고 Astra는 동정/검증과 원 Material 채택에 더 한정했다. 기존 지원 계산과 문서
연결을 사용하고 새 물리나 저장소를 추가하지 않는 제안이다.

이는 검토자의 권고이며 새 구현 배정으로 채택하지 않았다. 전체 범위를 Material로
줄이거나 CAD/FE·Post의 선행조건으로 삼지 않는다. 현재 배정과 다음 행동은
[CURRENT_STATE](../CURRENT_STATE.md) 한 곳에서 관리한다.

구현을 다시 진행할 때는 코드 파일이 아닌 사용자가 끝낼 업무를 배정하고, 처음부터
실행 가능한 통합본을 유지해야 한다. 동일 GUI 담당이 여러 창의 실제 작업을 검수하며,
독립 검토에서 생긴 사용 차단 지적은 같은 인도 안에서 닫아야 한다. 새 추상적 규칙집보다
이미 있는 제품계획·협업 규칙을 실제 산출물에 적용하는 것이 필요한 교정이다.

## 1. 목표, 제품 형태와 비용 조건

이번 작업의 목표는 다음 세 가지를 함께 완성하는 것이다.

브라우저나 localhost 페이지를 제품의 주 화면으로 만들지 않는다.

실제 데스크톱 작업 환경에서 자연스럽게 연결되도록 설계한다.

추가 지출은 0원이다.

- 이미 보유한 Codex·ChatGPT Pro 사용권에 포함된 범위만 사용한다.
- 새 유료 구독, 유료 API 호출, 추가 크레딧 구매, 유료 플러그인,
  유료 UI 라이브러리, 서버·호스팅 비용을 발생시키지 않는다.
- 결제수단 등록이나 자동 유료 전환을 요구하는 체험판을 사용하지 않는다.
- 무료 도구와 오픈소스를 우선하고 실제 필요한 기능의 무료 제공 범위를 확인한다.
- 라이브러리는 프로젝트의 사용·배포 방식에 맞는 오픈소스 라이선스 조건을 확인한다.

- Pro 사용 한도나 연결 문제가 생겨도 유료 API나 추가 구독으로 우회하지 않는다.
  제한을 정확히 알리고, Pro 응답에 의존하지 않는 작업은 계속한다.

전체 상세 기획과 화면 설계를 먼저 완성해 사용자에게 제시한다.
내가 이를 검토하고 제품 개발 시작을 지시한 뒤 본격적인 구현 단계로 넘어간다.

## 4. ADR과 검증이 개발을 방해하는 문제의 처리

52개 원요구 항목과 기존 ADR은 각각 요구와 설계 기록이다.
이를 동일한 크기의 기능이나 개발 과제로 취급하지 않는다.

ADR의 내용은 역할별로 정리한다.

- 현재 필요한 구조·책임·데이터 소유권의 결정:
  이유와 적용 범위를 간추려 현재 설계 기준에 남긴다.
  변경이 필요하면 이유, 영향과 대안을 검토하고 기록한다.

- 과거 벤치마크 결과·실패·환경·당시 검증 상태:
  과거 근거로 보존하고 현재 작업 지시와 분리한다.

- 앞으로 필요한 검증:
  관련 개발 항목에 연결된 검증 목록으로 묶는다.
  대상 기능, 목적, 수행 시점, 완료 기준과 재사용할 근거를 명시한다.

OpenScience, Core, Domain, Adapter의 책임 경계와
기존 native 모델·아티팩트 재사용 같은 유효한 설계 원칙은 이어간다.
과거 예제의 제한된 물리 범위, 특정 모델 지정, 당시 실행 순서,
“다음 검증” 문구를 전체 제품 개발의 상한이나 선행조건으로 적용하지 않는다.

현재 문서의 충돌을 해결하는 데 필요한 범위만 정리한다.
ADR 전체의 재작성·재실행을 별도 대형 과제로 만들지 않는다.

검증은 개발할 기능에 연결한다.
개발 중에는 해당 기능의 동작·저장·오류 처리와 영향을 받는 부분을 확인한다.
넓은 솔버 벤치마크와 최종 통합 검증은 관련 구현이 준비된 뒤 수행한다.
변경하지 않은 솔버·메시·물리 예제의 반복 검증으로 GUI 개발을 막지 않는다.

과거 실패, 측정값과 원래 수치 허용치를 보존한다.
미지원·미검증 표시만 추가하고 개발 완료로 처리하지 않는다.
알 수 없는 공학적 요구는 UNKNOWN으로 유지하며,
프로그램 동작 성공과 공학적 승인·출시 가능 판정을 구분한다.

## 5. 전체 개발 명세

목표 제품은 독립적으로 사용할 수 있는 로컬 공학 연구 도구군이다.

범위:
- FreeCAD 기반 CAD/FE Pre
- ParaView 기반 Post
- 독립 Data·Material·PDE·Numerical·Runner·Expert
- Study와 선택적 Workbench

기존 Qt/PySide6 앱과 FreeCAD·ParaView의 native 기능을 조사해 재사용한다.
기존에 구현된 기능을 처음부터 다시 만드는 것으로 범위를 바꾸지 않는다.
각 도구의 독립 사용과 도구 사이 데이터 전달을 함께 설계한다.

원요구와 최신 제품 요구를 사용자 작업 중심의 기능으로 재구성한다.
각 기능에는 다음을 명시한다.

- 누가 어떤 작업을 끝내기 위해 사용하는가
- 시작 조건과 처음부터 끝까지의 작업 흐름
- 사용자가 각 단계에서 보고 판단하고 조작하는 대상
- 입력·출력·단위·데이터와 저장·재열기 동작
- 화면·상태 변화·오류·취소·복구
- 기존 구현 위치와 재사용할 부분
- 빠진 기능과 추가·수정할 코드 및 서비스 연결
- 의존 관계, 구현 순서, 사용자 관점의 완료 조건

예를 들어 접촉 기능은 기준 문제의 정답 확인에 그치지 않는다.
사용자 모델의 면 선택, 법칙·마찰·간극 설정, 실행,
접촉 결과 확인, 저장과 형상 변경 후 참조 복구까지 개발 항목으로 정의한다.

필요한 기능과 현재 구현 여부를 분리한다.
기존 구현·추가 개발·외부 의존·미결정을 명확히 표시한다.
백엔드가 아직 없다는 이유로 요구 범위에서 조용히 제거하지 않는다.
유료 제품에만 의존하는 설계는 피하고 무료 구현 경로를 검토한다.
무료 경로가 확인되지 않은 요구는 누락시키지 말고 미해결 항목으로 남긴다.

## 6. 무료 기획 도구와 실제 데스크톱 GUI 상세 설계

기획에는 다음 도구를 사용한다.

A. draw.io Desktop
- 사용자 작업 흐름, 정보 구조, 도구 간 데이터 전달,
  화면 전환과 상태·복구 경로를 설계한다.
- 편집 가능한 .drawio 원본을 로컬에 보관한다.
- 유료 연동이나 별도 과금 AI 기능을 사용하지 않는다.

B. Penpot Professional 무료 플랜
- 실제 데스크톱 창 크기의 화면 설계, 재사용할 구성요소,
  상태별 화면과 클릭 가능한 작업 흐름을 만든다.
- 무료 플랜 안에서 작업하고 유료 체험·상위 요금제를 선택하지 않는다.
- 편집 가능한 원본과 로컬로 내보낸 산출물을 보관한다.
- 실제 접속·편집·내보내기가 가능한지 확인한다.
- Penpot은 설계 도구다. 제품 GUI나 필수 실행 환경으로 포함하지 않는다.

C. Qt Designer와 기존 Qt/PySide6 환경
- 주요 조작을 실제 데스크톱 창에서 확인하는 시제품을 만든다.
- 기존 Qt 구성과 호환되는 오픈소스 범위를 사용한다.
- 유지보수 가능한 .ui 파일이나 Qt 소스와 실행 방법을 제공한다.
- 도킹, 크기 변경, 키보드 조작, 선택, 표·그래프 연동,
  파일 대화상자처럼 그림만으로 판단하기 어려운 동작을 확인한다.

현재 도구의 설치·접속·무료 제공 범위를 먼저 확인한다.
연결이 필요한 계정이나 권한이 있으면 필요한 내용만 구체적으로 알린다.
도구 설치와 조사만 하고 기획 산출물 작성을 미루지 않는다.
무료 도구 사용에 문제가 생기면 동일한 수준의 편집 가능한 산출물을
만들 수 있는 무료 대안을 적용하고 변경 이유를 기록한다.
입력칸과 설명문만 있는 임시 웹 화면으로 대체하지 않는다.

설계 순서는 다음과 같다.

1) 대표 사용자 작업과 완료 결과 정의
2) 작업 순서·정보 구조·상태·오류 복구 설계
3) 화면 배치와 주요 조작의 대안 비교
4) 실제 제품 화면 수준의 상세 시안 작성
5) 주요 작업을 끝까지 따라갈 수 있는 상호작용 시안 작성
6) Qt 시제품으로 중요한 데스크톱 조작 확인
7) Pro와 독립 검토자가 사용 과정을 검토하고 교정

전체 화면 목록과 화면별 상세 명세를 작성한다.
메뉴와 입력 필드 목록만으로 기획을 완료하지 않는다.

각 화면에는 다음을 정의한다.

- 이 화면에서 사용자가 끝낼 작업과 주요 판단
- 메뉴, 툴바, 도킹 패널, 표·트리·그래프·3D 영역의 역할
- 선택·편집·드래그·컨텍스트 메뉴·대화상자·단축키의 동작
- 입력 형식, 단위, 기본값, 범위와 입력 사이 의존 관계
- 선택 없음, 빈 데이터, 편집 중, 미저장, 실행 중,
  실패, 취소, 완료 상태와 다음 행동
- Undo/Redo, 저장, 개정, 재열기와 도구 사이 이동
- 연결할 기존 명령·서비스와 새로 개발할 기능

예를 들어 Material 앱에서는 다음 전체 흐름을 설계한다.

시험 데이터 열기 → 열·단위 지정 → 곡선 구간 선택
→ 모델 피팅 → 원본·예측·오차 비교 → 계수 채택
→ 저장 → 다시 열고 작업 이어가기.

이 과정에서 필요한 조작을 먼저 정하고 입력칸과 버튼을 배치한다.
데이터 구조의 속성을 전부 폼으로 노출하는 방식으로 설계하지 않는다.
설명문을 계속 읽어야 다음 행동을 알 수 있으면 구조와 표시를 개선한다.
전문가가 반복해서 쓰는 작업은 불필요한 클릭과 입력을 줄인다.
상세 옵션은 작업 맥락에 맞게 제공하되 중요한 상태와 오류를 숨기지 않는다.

시각적 완성도도 기획에 포함한다.
글꼴, 색상, 아이콘, 컨트롤 높이, 간격, 정렬,
정보 밀도, 선택·포커스 표시와 접근성 기준을 일관되게 적용한다.
표·그래프·모델이 중심이 되는 정돈된 공학 도구 화면을 만든다.
실제 창 크기와 화면 배율에서 잘림·겹침·읽기 어려움을 확인한다.

기존 프로그램 캡처는 참고 자료다.
우리 제품의 구체적인 화면 시안과 편집 가능한 원본을 제출한다.
기존 22쪽 PDF나 예전 웹 시안이 있다는 이유로 완료 처리하지 않는다.
시안용 데이터와 가짜 계산은 명확히 구분한다.
클릭 가능한 시안의 완성과 실제 계산 기능의 구현 완료를 혼동하지 않는다.

## 7. 산출물과 완료 조건

기존 문서의 역할을 활용하고 같은 내용을 여러 곳에 복사하지 않는다.
다음 결과가 서로 연결되어 있어야 한다.

1) 최신 작업 범위와 간결한 운영·설계 기준
2) 전체 기능 개발 명세와 구현 작업 목록
3) 사용자 작업 흐름·정보 구조·상태 전이의 편집 가능한 도면
4) 전체 화면 목록과 구체적인 상태별 화면 설계
5) 주요 작업을 끝까지 따라갈 수 있는 상호작용 시안
6) 중요한 조작을 실제 창에서 확인할 수 있는 Qt 시제품
7) 요구사항 → 기능 → 화면 → 구현 대상 → 완료 조건의 대응표
8) 기능별 검증 목록과 최종 통합 검증 계획
9) 선택한 무료 도구·라이브러리, 사용 범위와 라이선스 확인 기록
10) Pro의 주요 판단, 독립 검토, 수정 사항과 남은 사용자 결정

완료는 문서·페이지·입력칸·검사 수로 판단하지 않는다.

내가 화면과 시제품을 보면서 실제 작업을 어떻게 시작하고,
무엇을 조작해 어떤 결과를 얻고, 잘못됐을 때 어떻게 복구하는지
확인할 수 있어야 한다.

개발자는 핵심 동작을 추측하지 않고 구현할 수 있어야 한다.
시안의 편집 가능한 원본, 실행 방법과 검토 자료가 로컬에 남아야 한다.
설계가 Windows 로컬 데스크톱 제품으로 이어지고,
추가 유료 도구나 서비스에 의존하지 않아야 한다.

상세 기획 단계에서 과거 솔버 검증 전체를 다시 통과할 필요는 없다.
기술 확인은 실제 설계 결정을 내리는 데 필요한 범위로 제한한다.
일상적인 조사·작성·교정마다 재승인을 요청하지 않는다.
이미 답한 제품 방향을 다시 묻지 말고,
실제로 남은 중요한 선택만 정리해 제시한다.

사용자 변경을 보존하고 의미 있는 결과를 저장소에 기록한다.
CURRENT_STATE, HANDOFF와 요구사항 상태를 실제 진행에 맞게 갱신한다.
검토한 변경을 의미 있는 단위로 커밋하고,
원격 반영 여부는 확인한 사실대로 보고한다.

산출물을 검토 가능한 상태로 제시한 뒤 내 개발 시작 지시를 기다린다.
개발이 시작되면 같은 역할 분담으로 Pro가 기능 단위 코드를 작성하고,
Codex가 검토·실행·통합하여 명세의 완료 조건까지 마무리한다.

지금은 MoAI 연결과 현재 맥락 확인부터 진행하고,
실제 Pro 협업과 무료 기획 도구를 사용해 위 산출물을 작성하라.
준비 완료나 진행 계획 설명만으로 작업을 끝내지 마라.

# Open-source contact and post-processing integration notes

Checked 2026-10-13 against the current public project sources and documentation. This is a bounded source review, not an installation, solver run, or validation campaign. The product baseline provided for this review was main `680af8e` and Pro's contact-editor work `e916a32`; this note does not claim those implementations were executed.

## PrePoMax with CalculiX

The official [PrePoMax downloads page](https://prepomax.fs.um.si/downloads/) identifies the source repository as [MatejB/PrePoMax on GitLab](https://gitlab.com/MatejB/PrePoMax), and states GPL-3.0 licensing. Its manual treats a contact surface interaction (the law) and a contact pair (the two regions) as distinct objects. Users can define surfaces/sets first or pick geometry/mesh entities in the feature dialog; the interaction menu supports separate creation/editing of surface interactions and contact pairs, master/slave swapping, and merging pairs by master/slave. The current source makes this separation concrete: [`CaeModel/Contact/ContactPair.cs`](https://gitlab.com/MatejB/PrePoMax/-/blob/master/CaeModel/Contact/ContactPair.cs) stores the law name, method, master/slave region names and types, and source selection IDs/data; [`SurfaceInteraction.cs`](https://gitlab.com/MatejB/PrePoMax/-/blob/master/CaeModel/Contact/Surface%20interaction/SurfaceInteraction.cs) owns the interaction-property list; and [`CalculixFileWriter.cs`](https://gitlab.com/MatejB/PrePoMax/-/blob/master/CaeModel/FileInOut/Output/Calculix/CalculixFileWriter.cs) serializes the surfaces, interactions, and pairs through distinct writer methods (`AppendSurfaces`, `AppendSurfaceInteractions`, `AppendContactPairs`). This is a useful code-level precedent for preserving pair/law/region identity. It does not establish that unrelated bodies should be fused or that coincident nodes should be merged. See the [v2.0 manual](https://prepomax.fs.um.si/wp-content/uploads/2023/12/PrePoMax-v2.0.0-manual.pdf) and the [current documentation index](https://prepomax.fs.um.si/documentation/).

The manual provides named unit-system options (`M_KG_S_C`, `MM_TON_S_C`, `M_TON_S_C`, `IN_LB_S_F`, `UNIT_LESS`) when opening a model; the downloads page also records a unit-system default change in v2.1. These are application-level conventions that a document/import path must preserve and report. They are not evidence that CalculiX input files carry an intrinsic unit system, so product-side values must remain tied to the document's declared units rather than inferred from numbers.

PrePoMax issue [#14, mixed solid and shell parts misrecognized](https://gitlab.com/MatejB/PrePoMax/-/issues/14) records a geometry-import failure where a STEP assembly's solid and shell were both treated as shells; importing separately was the reported workaround, while the maintainer pointed to OCCT/STEP interpretation and warned that blindly converting every closed surface could misclassify intentionally closed shells. This is an import/topology issue, not evidence for merging independently meshed bodies. It reinforces preserving body and mesh identity through import and making topology repairs explicit.

**Application to this product:** represent one contact pair as two independently identified regions plus a separately identified interaction law. A region may gather multiple selected faces, but that is a selection/serialization union, not a Boolean union of solids or node merge. Keep each body's nodes and element IDs independent; keep explicit contact/gap geometry as modeled. Do not add a physical gap automatically to work around a native-mesher limitation. Preserve the declared unit system, pair ordering, law, friction parameters, and source surface references in the exported model and provenance.

## CalculiX FRD to ParaView (`ccx2paraview`)

The [ccx2paraview source repository](https://github.com/calculix/ccx2paraview) is GPL-3.0. Its README requires ASCII FRD and instructs the user to request `*NODE FILE`, `*EL FILE`, and `*CONTACT FILE`; it writes VTK/VTU and a PVD collection for multi-increment output. It warns that one VTU is written per output interval (so 300 increments create 300 files), and suggests ParaView's `PVDReader`/`SaveData` route for bundling time steps into VTKHDF. See [README output guidance and API](https://github.com/calculix/ccx2paraview#general-remarks).

Source inspection of [`ccx2paraview/common.py`](https://github.com/calculix/ccx2paraview/blob/master/ccx2paraview/common.py) found a generic nodal FRD reader: `NodalResultsBlock` captures variable name, components, node-indexed values, step and increment; `FRD.parse_mesh` builds one unstructured grid from the FRD node/element blocks; `FRD.parse_results` appends result arrays to that grid; and `Converter` emits one file per `(step, increment)` plus PVD. The generic reader can represent standard nodal result blocks, but it does not attach contact-pair/surface identity to result arrays or construct separate pair datasets. Thus requesting `*CONTACT FILE` is necessary to obtain CalculiX contact output, but this inspection does not verify pair-aware contact visualization, field coverage, or preservation of multiple mesh namespaces. The README also explicitly describes FRD as node-based and says element results are stored at nodes after extrapolation; do not label these arrays as integration-point results.

The public issue list includes [#56, dynamic conversion skips the zero-th time step](https://github.com/calculix/ccx2paraview/issues/56), [#41, request to select which timestep is written](https://github.com/calculix/ccx2paraview/issues/41), and [#8, opening multiple time-step files together](https://github.com/calculix/ccx2paraview/issues/8). These are useful evidence that step/increment and time-series behavior need explicit tests and that output-file count matters. The repository's tests are converter tests, not a contact engineering validation suite.

The same source contains two concrete behaviors to account for before direct reuse: `read_nodal_results` initializes all node component arrays to zero, and `convert_frd_data_to_vtk` replaces infinity/NaN with zero. An absent contact row or invalid value could consequently look like a measured zero. This is source inspection, not a reproduced converter run. Our adapter must retain row coverage and invalid values separately from display arrays.

**Application to this product:** evaluate the existing converter's mesh/VTK and time-series components before writing replacements. Preserve run, step/time, field and node identity in the existing product result records; retain pair membership from the frozen model where FRD lacks it. Compare an adapted converter with extending our existing strict FRD reader; choose based on actual missing behavior and integration size. GPL-3.0 is a free reuse option, not a reason by itself to reject the project. No code was copied or dependency installed in this review. Redistribution of copied/modified code needs the applicable license notices and source obligations; this repository's own distribution license is not yet declared. Optional external use remains a candidate. Do not install a separate VTK package over the existing ParaView runtime merely to try the converter.

## FreeCAD evidence supplied by the integration lead

The [FreeCAD FEM Geometry Preparation and Meshing wiki](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/FEM_Geometry_Preparation_and_Meshing.md) documents that the current workflow does not support multiple meshes in one analysis model and describes meshing a single Boolean-merged assembly. It distinguishes touching bodies, which can yield a continuous mesh, from separated bodies, which require contact. **Product interpretation:** this describes a native workflow constraint, not an engineering requirement to erase independent body/node identities or introduce an artificial physical gap. Our contact model should retain separate regions and mesh identities while exposing the actual mesher limitation to the user.

As of 2026-10-13, [FreeCAD PR #30844](https://github.com/FreeCAD/FreeCAD/pull/30844) was marked Draft/WIP and proposed coincident-node merging; it was not evidence of an integrated, verified export workflow. A contributor specifically objected that automatic export merging is not user-inspectable/controllable and can break intended contact behavior (discussion lines 487–492). Do not adopt it as our contact-node merge implementation. [Issue #8610](https://github.com/FreeCAD/FreeCAD/issues/8610) says the GUI view provider performs tessellation while headless use calls it directly; [issue #7393](https://github.com/FreeCAD/FreeCAD/issues/7393) reports a GUI/CLI tessellation difference in 0.20 and was closed as `not planned`. These are related observations, not proof that the present preview defect has the same cause.

The [FreeCAD 1.1.4 `TopoShapePyImp.cpp`](https://github.com/FreeCAD/FreeCAD/blob/1.1.4/src/Mod/Part/App/TopoShapePyImp.cpp) API shows `copy()` defaulting to `copyGeom=True, copyMesh=False`, calls `makeElementCopy`, and implements `cleaned()` by copying then calling `BRepTools::Clean`. Separately from this source review, Pro's `37916e8` correction uses copies for preview. Codex integrated it as `71f3e03` and checked the real FreeCAD two-foot model through multi-face contact declaration, invalid draft correction, separate empty mesh objects and save/reopen. Only GUI presence/selection queries were stubbed. This closes the reproduced preview mutation in that path; it does not establish meshing, contact solving or native window usability. See [the contact workflow record](../CONTACT_WORKFLOW.md).

## Decision and limits

Keep a face-set union as region membership, preserve body/mesh/node identity, and keep pair/law/time/unit data separate in the common result model. Do not use a mesher's single-mesh restriction as a reason to mutate physical geometry or silently merge nodes. No FreeCAD, PrePoMax, solver, or ParaView code was installed or run for this note; source references establish design behavior and limitations only.

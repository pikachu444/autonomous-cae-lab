# Codex 개발 운영 지침

2026-10-07 · 모델·토큰·분업·재개 규칙 · 제품 설계와 별도

## 1. 읽을 문서와 책임

이 문서는 제품을 만드는 Codex의 작업 방법을 정한다. 제품 안의 재료/시험 전문가, OpenScience 설정, 솔버 권한을 정하지 않는다. 기존 설계와 사용 사례는 유지한다.

| 파일 | 답하는 질문 | 읽는 시점 |
|---|---|---|
| `AGENTS.md` | 무엇을 만들고 어떤 원칙으로 작업하는가? | 모든 개발 세션의 진입점 |
| `docs/WORKBENCH_REDESIGN.md` | W1–W5의 구조·API·구현·완료 범위는 무엇인가? | 첫 착수 때 전체 연결, 이후 해당 절 |
| `docs/WORKBENCH_USE_CASES.md` | 어떤 연구를 실제로 할 수 있어야 하는가? | 첫 착수 때 대표 흐름, 이후 관련 사례 |
| `docs/CODEX_WORKFLOW.md` | 누가 구현하고 어떻게 비용·분업·재개를 관리하는가? | 첫 착수·재개 때 |
| `docs/DEVELOPMENT_SKILLS.md` | 어떤 기존 스킬을 언제 호출하는가? | 첫 착수 때 선택표, 호출 때 해당 원문 |
| `CODEX_START.txt` | 새 세션에서 어디부터 시작하는가? | 사용자가 전달할 시작 지시 |

이전 대화나 첨부 PDF를 새 세션이 기억한다고 가정하지 않는다. 현재 Markdown을 기준으로 삼는다. 원본 설계 전체를 각 보조 에이전트에 반복해서 복사하지 않는다. 필요한 절과 전역 제약만 전달한다. 과거 ADR는 해당 동작의 근거가 필요할 때 찾는다. 같은 내용을 여러 문서에 복제하지 않는다.

## 2. 이번 저장소의 개발 설정

**기본 선택:** 주 담당 `gpt-6-astra` / `high`, 보조 `gpt-6.1-sol` / `high`, 동시에 열린 보조 스레드 최대 2개. 주 담당은 별도다. 이것은 초기 개발 운용값이며 제품 제한이 아니다.

이전 시작 파일의 Astra `xhigh` 상시 권고는 이 기본값으로 조정한다. 이유는 최고 추론을 반복 조사·일반 구현까지 적용하는 비용을 피하기 위해서다. 어려운 공통 경계·수치 문제에는 여전히 `xhigh`를 사용한다. 이는 이 저장소에서 수행한 모델 비교 실험의 결론이 아니라 작업 위험과 비용을 고려한 권고다. 공식 모델/설정 자료는 문서 끝에 있다. [O1–O3]

| 역할/상황 | 기본 모델·추론 | 사용 조건 |
|---|---|---|
| 주 담당 | Astra High | 전체 요구 유지, 직접 구현, 공통 경계, 최종 통합 |
| 공통 설계 충돌·어려운 수치 오류 | Astra Extra High | 원인·상충 요구와 종료점을 정한 해당 작업만. 실제 선택을 확인 |
| `reuse_researcher` | Sol High | 기존 코드·공식 자료·라이브러리 조사. 구현을 막는 질문에 답하면 종료 |
| `bundle_worker` | Sol High | 인터페이스와 쓰기 범위가 정해진 기능 구현 |
| `integration_reviewer` | Astra High | 공통 API·수치 의미·통합 결과에 중요한 변경이 있을 때 |

일반 수정마다 독립 Astra 검토를 붙이지 않는다. 작은 수정은 주 담당의 검토와 관련 검사로 끝낸다. 주 담당을 Sol로 바꾸는 절약안은 가능하지만, 기본 운영값을 몰래 바꾸지 않는다. 사용자가 직접 고른 설정을 알리지 않고 덮어쓰지 않는다.

**실제 파일:** `.codex/config.toml`과 `.codex/agents/*.toml`에 위 값을 넣는다. 프로젝트를 신뢰한 Codex가 읽는 설정이다. 사용자·조직 설정과 명시적 실행 인자가 실제 값에 영향을 준다. 시작 때 선택된 모델/추론·보조 기능·프로젝트 신뢰 여부를 확인한다. 확인할 수 없는 값은 미확인으로 표시한다. [O2, O3]

설정 파일이 저장됐다는 사실과 사용자 PC에서 활성화됐다는 사실은 다르다. 계정에 없는 모델을 선언해도 접근 권한이 생기지 않는다. 미지원 키나 모델 오류는 해당 설정만 호환하게 조정한다. 별도 설정관리 프로그램을 만들지 않는다. 인증·전역 설정·샌드박스 권한·제품 연구 모델은 이 작업에서 바꾸지 않는다.

속도 모드는 Standard를 권한다. 프로젝트 파일에는 기존 속도 설정을 덮어쓸 `service_tier`를 넣지 않는다. 현재 Fast/Ultrafast가 켜져 있으면 시작 보고에서 알린다. 사용자의 속도 선택을 묵시적으로 바꾸지 않는다. Max/Ultra도 기본으로 강제하지 않는다.

## 3. 토큰과 작업 비용

Astra를 많이 쓰면 사용량 부담이 커질 수 있다. 병렬 에이전트도 각각 모델과 도구를 사용한다. 병렬화는 시간을 줄일 수 있지만 토큰 절약을 보장하지 않는다. 더 높은 추론 수준도 더 많은 시간과 토큰을 사용할 수 있다. [O1–O4]

2026-10-07 공식 Standard 구매 크레딧 표는 백만 토큰당 Astra 입력/출력 250/1250, Sol 50/250이다. 캐시 입력은 각각 25/2.5다. 따라서 같은 비캐시 입력·출력 토큰 수의 요율은 5배, 캐시 입력 요율은 10배다. **이 비율이 개인 Pro의 사용 가능 시간·작업 수 비율을 뜻하지는 않는다.** 구독 제한과 실제 차감은 계정·모드·작업에 따라 확인해야 한다. 사용자 계정의 남은 한도는 이 문서에서 알 수 없다. [O4]

목표는 호출 1회의 최저 가격이 아니라, 성공한 기능을 얻는 전체 비용이다. 전체 비용에는 구현·검토·실패 재작업이 들어간다. 강한 모델이 재작업을 줄일 가능성은 있지만 이 저장소에서 수치로 검증하지 않았다. ‘전부 최고 모델이면 한 번에 끝난다’고 가정하지 않는다.

실제 운용은 다음과 같다.

1. 시작과 기능 묶음 종료 때, 제공되는 사용량 화면/상태를 확인한다. 숨겨진 한도나 토큰 수를 추정해 사실처럼 쓰지 않는다.
2. 주 담당은 전체 결정을 소유한다. 보조에게는 필요한 질문·절·파일만 준다. 원시 로그와 저장소 전체를 각자 다시 읽히지 않는다.
3. 같은 조사나 검사를 여러 에이전트에게 중복 배정하지 않는다. 독립 검토가 목적이면 중복 범위와 이유를 명시한다.
4. 보조가 끝나면 결과를 수집하고 스레드를 닫는다. 대기만 하는 스레드를 계속 남기지 않는다.
5. 사용량 경고가 나오면 새 분업을 줄이고 안전한 인계 위치를 남긴다. 추가 크레딧 구매·API 과금·계정 변경을 자동으로 하지 않는다.
6. 같은 실패를 코드/입력/환경 변경 없이 반복하지 않는다. ‘검증용 검증’과 여러 번의 동일 전수 읽기를 피한다.
7. 문맥이 길어지면 완료 결과·현재 결정·남은 작업을 압축한다. 모델이 모든 이전 내용을 계속 기억할 것이라고 가정하지 않는다.

**한 번에 제대로**는 전체 W1–W5를 거대한 단일 호출로 끝내라는 뜻이 아니다. 공통 경계를 제대로 정하고, 실제 기능 묶음을 완성하고, 같은 목표를 유지하며 다음 묶음으로 가라는 뜻이다.

## 4. 분업과 통합

주 담당은 관리자 역할만 하지 않는다. 구현에도 참여한다. 제품 범위, 공통 API, 작업 순서, 통합·최종 판단을 직접 책임진다. 보조가 반환한 ‘완료’를 그대로 전체 완료로 옮기지 않는다.

```text
주 담당 Astra — 전체 목표 / 공통 경계 / 직접 구현 / 통합
  ├─ 필요한 조사 → reuse_researcher (Sol)
  ├─ 분리 가능한 구현 → bundle_worker (Sol)
  └─ 중요한 변경 검토 → integration_reviewer (Astra)
동시에 열린 보조는 기본 2개 이내. 역할 셋을 상시 실행하지 않는다.
```

W1–W5를 다섯 에이전트에게 동시에 통째로 맡기지 않는다. W1 경계가 연결되기 전에는 주 담당 구현과 관련 조사부터 시작한다. 경계가 연결되면 W2 수치 기능, W3 실행 연결, W4 자료 검색 중 독립된 일을 나눈다. W4 계산 위임은 W3의 같은 작업 관리에 연결한다. W5 화면은 실제 API를 소비한다. 보조에게 재귀적인 재위임은 허용하지 않는다.

### 보조 작업에 전달할 내용

| 항목 | 전달할 값 |
|---|---|
| 사용자 결과 | 해당 W와 사용 사례, 끝나면 사용자가 할 수 있는 일 |
| 입력과 근거 | 필요한 문서 절, 기존 코드·실행 결과, 알고 있는 제약 |
| 소유 범위 | 수정 가능한 파일/영역 또는 조사·검토 전용 범위 |
| 계약 | 입력·출력·단위·오류·다른 코드가 사용할 인터페이스 |
| 반환과 종료 | 변경/삭제 책임, 실제 결과·출처, 남은 장애, 끝낼 지점 |
| 실행 예산 | 선택 모델/추론, 필요한 실행 범위, 새 비용·권한 금지 |

같은 파일을 동시에 수정하지 않는다. 공통 API 변경은 주 담당이 먼저 정하고 소비 경로까지 통합한다. 서로 독립된 파일에 한해서 병렬 구현을 허용한다. worktree가 필요하면 기존 Git 기능을 사용한다. 사용자가 Git 명령·커밋 번호를 직접 관리하게 하지 않는다.

보조가 작업을 넓히거나 같은 실패만 반복하면 주 담당이 범위를 다시 정한다. 새 관리자 에이전트를 추가해서 해결하지 않는다. 보조 기능이 없으면 동일 책임을 순차 수행하고 실제 병렬·독립 검토를 했다고 말하지 않는다.

## 5. W1–W5를 끝까지 연결하는 운영

아래 표는 기존 명세의 요약 연결이다. 상세 API·완료 조건은 설계 문서를 따른다.

| 작업 | 주 담당의 통합 책임 | 보조에게 맡길 수 있는 일 | 사용자 결과 |
|---|---|---|---|
| W1 | 독립 실행·조회·확장 경계 | 선택 import/기존 어댑터 경로 조사 | 직접 함수·기존 비-CAD 실행·솔버 없는 조회 |
| W2 | 동정/DOE/결과의 공통 연결 | 준비 객체·표본·라이브러리 비교, 분리된 구현 | 다중 계수·곡선, 후보표, 상태 분리, 실제 비용 |
| W3 | 같은 작업 소유와 권한 | 중복 실행 경로 추적, 분리된 transport 구현 | GUI/CLI/MCP의 같은 작업·중단·결과 |
| W4 | 자료→전문가→실제 계산 | 자료 검색 또는 한정된 모델 연결 | 출처 있는 후속 대화, 자문, 실제 실행 결과 |
| W5 | 설치와 사용자 흐름 A–D | 화면·사용법의 독립 구현/관찰 | 사용자가 자료/값을 바꿔 재실행하고 보고서 작성 |

매 묶음마다 네 가지 축을 놓치지 않는다. 재료/시험 동정, CAD 없는 방정식·수치 연구, 기존 결과 분석, 불량 자문·계산 위임이다. 기존 CAD·implicit·explicit 경로도 지원 목록에서 사라지지 않게 한다. 한 묶음에서 전부 구현하라는 뜻은 아니다. 쉬운 CAD 예제나 작은 검사만 전체 목표로 바꾸지 말라는 뜻이다.

함수·폴더·테스트 수가 아니라, 실제 입력→계산/검색→결과→소비 API/화면으로 완료를 판단한다. 브라우저 설명용 계산기·규칙 기반 자문·작성한 동영상은 제품 솔버/실제 에이전트 실행의 증거가 아니다. 작은 UI 문구 문제를 실제 수치 오류와 같은 중단 사유로 다루지 않는다.

소스나 입력이 잘못되어 결과가 틀리면 해결한다. 데이터 손상·접근권한·잘못된 종료도 해결한다. 과거 profile/prompt 지문 보존 검사가 새 설계와 충돌하면 현재 기능을 확인하는 검사로 바꾼다. 파일 검사·잠금을 이유 없이 모두 제거하지 않는다.

## 6. 조사·스킬·검토를 실제 개발에 연결

스킬 원본과 선택·설치 상태는 `docs/DEVELOPMENT_SKILLS.md`에서 관리한다. 새 공통 기반이나 중요한 의존성이 필요하면 기존 코드와 공식 자료를 먼저 조사한다. `research`를 사용하고 아래 판단을 한 곳에 남긴다.

- 필요한 기능, 현재 구현 위치, 유력한 재사용 후보와 출처.
- Windows/WSL 설치, 실행 비용·메모리·병렬성, 유지보수·라이선스·교체 비용.
- 재사용/얇은 연결/수정/직접 구현 중 선택, 없어질 코드와 필요한 연결.

후보 개수를 맞추는 의식은 만들지 않는다. 답이 명백한 작은 수정마다 조사 보고서를 만들지 않는다. 조사 결과는 해당 결정 절에 한 번 기록하고 코드에 반영한다. 중요한 설계 변경에는 독립 검토를 사용한다. 검토자는 실제 수치·단위·상태·사용 흐름·복잡성·외부 구현 재사용을 본다. 근거 없는 미관 지적이나 과거 형식 복원은 완료를 막지 않는다.

`grill-me`는 아직 결정하지 않은 중요한 쟁점에만 쓴다. 현재 W1–W5와 직접 사용·OSS 재사용·MCP 선택 원칙을 처음부터 묻지 않는다. 사용자에게 물어볼 사실은 먼저 코드와 문서에서 찾는다. 답이 필요한 쟁점에는 권장안과 영향만 설명한다. 그 답과 무관한 작업은 계속할 수 있다.

## 7. 중단·인계·문맥 유지

진행 요약은 **현재 PR의 갱신 가능한 진행 댓글 하나**를 우선 사용한다. 연결이 없을 때만 기존 로컬 진행 기록 한 곳을 사용한다. 두 곳을 경쟁하는 상태 원본으로 운영하지 않는다. 큰 HANDOFF 문서나 상태 DB를 새로 만들지 않는다.

```text
현재 브랜치 / 마지막 반영 위치
실제 사용할 수 있게 된 기능과 입력·실행·결과 위치
W1–W5에서 완료 / 진행 / 외부 환경 대기 / 미시작
공통 API와 의존성 선택 중 다음 세션에 필요한 결정
실행한 검사, 실패 원인, 하지 못한 실제 solver/LLM 확인
진행 중인 프로세스·보조 작업, 다음에 수정할 위치와 사용자 결과
```

첫 세션에는 전체 연결과 관련 문서를 읽는다. 이어지는 세션은 위 요약과 바뀐 파일을 읽고 중단 지점에서 계속한다. 계정/솔버가 없으면 그 실제 연결만 미확인으로 남기고 독립 구현을 진행한다. 세션 종료를 제품 완료로 표시하지 않는다. 자동 재개 도구를 실제로 쓰지 않았으면 나중에 알아서 계속한다고 약속하지 않는다.

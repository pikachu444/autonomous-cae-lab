## 1. 이번 작업의 목적과 문서 우선순위

최종 목표는 사용자가 로컬에서 자료와 모델을 넣고, 계산·시험 비교·동정·DOE·영향도 분석을 수행하며, 필요할 때 실제 전문가 LLM이 자료를 읽고 다음 연구를 실행 가능한 계획으로 제안하는 연구 작업대다. CAD, OpenScience, MCP, AI는 모든 계산의 선행 조건이 아니다. 상용 솔버의 별도 ASCII 결과도 같은 연구에 참여한다. LS-OPT는 사용할 수 없다. 칩 충격시험은 예시이며 제품의 도메인·계수·하중 채널을 고정하지 않는다.

현재 코드를 버리거나 W1부터 다시 구현하지 않는다. FELUPE/SciPy 계산, 파일 읽기, 기록, 작업 관리자, Haystack 검색/Agent, 기존 어댑터와 화면을 재사용한다. 이번 완료는 ‘코드가 있다’가 아니라 **로컬에서 실제 도구와 연결된 사용자 흐름을 실행했다**는 뜻이다.

## 3. 로컬 시작과 멀티에이전트 분업

### 3.1 코드 기준과 개발 환경

사용자가 선택한 로컬 폴더에서 작업한다. 저장소가 없으면 Codex가 가져온다. 원격 main을 fetch하고 로컬 변경·현재 분기와 차이를 확인한다. 사용자 변경을 보존한 구현 브랜치를 최신 main에서 만든다. 기존 구현 작업이 있으면 차이를 통합하고 중복 구현하지 않는다. 과거 PR #1의 미병합 브랜치에서 다시 시작하지 않는다. Git 명령이나 커밋 번호 관리를 사용자에게 떠넘기지 않는다.

Windows와 WSL을 같은 환경으로 취급하지 않는다. 서비스 Python, 솔버 실행 위치, 작업 폴더와 경로 변환을 먼저 정한다. 기존에 준비된 환경을 우선 사용한다. Linux 의존 솔버에는 로컬 WSL/컨테이너를 사용할 수 있다. Windows 설치 솔버도 등록된 명령으로 연결할 수 있다. 이를 위해 전체 제품을 Windows 전용 또는 WSL 전용으로 다시 만들지 않는다.

이번에는 Codex Cloud, GitHub Actions, 원격 서버에서의 실행을 **사용자 로컬의 준비 완료 증거로 대체하지 않는다.** GitHub는 코드 동기화·PR·보조 CI에 사용한다. 로컬 앱·솔버의 실제 동작을 확인한다. 로컬 명령 실행이 곧 오프라인 LLM이라는 뜻도 아니다. 회사 자료와 모델 전송 범위는 별도다.

### 3.2 역할과 소유권

기존 설정과 역할을 재사용한다. 주 담당은 Astra High, 독립 보조는 Sol High, 중요한 통합 검토는 Astra High를 권한다. 실제 계정/클라이언트에서 확인한 모델만 사용한다. Extra High는 어려운 공통 경계·수치 원인 분석에 한정한다. 개발 모델 선택과 제품의 전문가 모델 인증을 혼동하지 않는다.

| 담당 | 구체 업무 | 기본 수정 범위 | 반환 산출물 |
|---|---|---|---|
| 주 담당 | API·응답·권한 계약, 전체 실행 흐름, 직접 구현·최종 통합 | `evaluation.py`, `workbench.py`, `jobs.py`, 공통 경계 및 통합 결정 | 합의한 계약, 통합 코드, 실제 전체 사용 결과 |
| 보조 A: 로컬 솔버/수치 | 4절 설치·실행, 5절 reader/네이티브, 7절의 분리된 수치 연결 | 배정한 adapters·worker·설치 코드·해당 수치 모듈 | 실제 실행 명령/버전/원본 결과, 채널 매핑, 원인과 수정 |
| 보조 B: 전문가/화면 | 6절 스키마·권한 화면·후속 대화, 8절 UI | 배정한 `assist/`, `apps/lab/static/`, 해당 routes | 유효 요청, 승인·자문·계산·결과 회수 흐름, 실제 화면 결과 |
| 독립 검토자 | 중요한 기능 묶음의 수치 의미·실사용 누락 검토 | 읽기 전용; 수정은 주 담당에 요청 | 근거 있는 결함, 예상 동작과 실제 실행 확인 |

동시에 열린 보조는 기본 2개다. 검토자는 보조 하나가 끝난 후 그 자리를 사용한다. 새 에이전트 OS나 재귀 위임은 만들지 않는다. 역할이 없으면 기존 `bundle_worker`에 범위를 전달한다. 설정파일을 늘려 역할 수 자체를 성과로 삼지 않는다.

각 작업에는 목표 사용자 행동, 참조 절, 입력, 수정 파일, API 계약, 실제 확인 방법, 반환물, 종료점을 준다. 같은 파일을 동시 수정하지 않는다. 인터페이스 변경은 주 담당이 먼저 확정하고 소비 코드까지 통합한다. 주 담당은 조사가 끝날 때까지 대기만 하지 말고 독립된 실제 구현을 진행한다.

권장 순서는 **짧은 환경/계약 확인 → 보조 A의 로컬 실행·응답과 보조 B의 전문가 입력·화면 병행 → 주 담당 통합 → 실제 모델/사용자 흐름 → 독립 검토**다. 새 코드가 연결될 때마다 관련 결함을 해결한다. 전체 pytest나 감사 보고서부터 반복하지 않는다.

### 3.3 기존 스킬

`.agents/skills/research/SKILL.md`와 개발 스킬 지침을 사용해 바꿀 기능에 필요한 공식 API·기존 구현을 조사한다. 새 스킬부터 만들지 않는다. 연구 질문을 정하고 소스·버전·선택 이유를 짧게 남긴 뒤 코드에 반영한다. `grill-me/grilling`은 문서·코드·검색으로 답을 찾을 수 없는 중요한 사용자 선택에만 쓴다. 이미 합의한 제품 범위를 다시 인터뷰하지 않는다. Context7 등은 사용 가능하면 활용하고 설치를 선행 프로젝트로 만들지 않는다. Ouroboros 전체는 필수 도입하지 않는다.

## 4. R1 — 로컬에서 실제 솔버를 준비하고 실행한다

**수정 위치:** 기존 설치/실행 스크립트, `caelab/workbench_cli.py`, `backends.py`, 해당 adapters/worker, `docs/LOCAL_EXECUTION.md`. 기존 진단을 확장하며 독자 설치관리 플랫폼은 만들지 않는다.

1. 선택된 서비스 Python, Windows/WSL/컨테이너 위치, CPU/RAM/디스크, 실행파일·공유 라이브러리·컴파일러·네트워크를 실제로 확인한다. 비밀 값은 출력하지 않는다.
2. OpenRadioss, Code_Aster, FEniCSx, MFront/MGIS/MTest의 현재 사용 가능한 설치를 찾는다. 기존 설치를 재사용하고 필요한 것만 준비한다. 배포본 설치/기존 패키지 관리/공식 빌드 절차 중 적합한 경로를 선택한다. `pip install` 성공을 네이티브 설치로 계산하지 않는다.
3. OpenRadioss의 과거 URL 404는 배포·DNS·프록시·권한·주소 문제를 구분해서 조사한다. 실제 official release 자산을 확인한다. 공식 소스 빌드가 필요하면 기존 HOWTO를 사용한다. 다운로드가 안 된다는 이유로 오래된 링크/지문을 고정 보존하거나 무작위 바이너리를 설치하지 않는다. 바뀐 배포본은 버전/출처와 실제 실행을 확인한다.
4. Code_Aster 실패 사례를 원본 덱과 함께 재현한다. 단위·스케일·구속·요소·선형계 잔차를 확인하고 검증된 설정/모델 수정으로 해결한다. MUMPS 정밀도 오류를 설치 실패로 표시하지 않는다. 허용 오차만 올리고 종료 코드 0을 얻는 방식은 금지한다.
5. FEniCSx 벡터 사례는 기준해·오차 적분·경계조건·격자별 수렴을 본다. 이론과 실행 결과로 타당한 검사 구간을 정한다. 근거 있는 검사 수정은 허용하지만 실패값에 맞춰 기준을 낮추지 않는다. 반복 잔차와 이산화 오차를 구분한다.
6. MFront는 MGIS/MTest와 실제 법칙 로딩·응력 업데이트를 확인한다. 일반 실행에서 특정 개발 PC 바이너리 지문 일치만을 이유로 다른 정상 설치를 거부하지 않도록 벤치마크 규칙을 분리한다.
7. 선택 backend의 doctor는 발견/의존성/실제 실행을 구분해 표시한다. 실행 확인은 사용자가 요청한 backend에 대해서만 한다. 결과만 읽는 사용자에게 모든 솔버 설치를 요구하지 않는다.

**완료 행동:** 로컬에서 실제 입력을 바꾼 작은 계산을 실행하고 명령·환경·원본 출력·실패 원인을 저장한다. OpenRadioss의 starter와 engine을 모두 확인한다. Code_Aster/FEniCSx/MFront의 관련 계산은 앞선 무관한 검사 하나의 실패 때문에 모두 건너뛰지 않도록 독립 실행 가능하게 한다.

관리자 권한·재부팅·외부 인증·대용량 설치 승인이 실제로 필요할 때만 정확한 요청을 한다. 필요한 승인과 사용자 개입을 무시할 수는 없다. 승인 대기는 진행 중인 상태이지 완료가 아니다. OpenRadioss가 막혀도 다른 reader/UI를 계속 구현하지만 explicit 준비 완료라고 쓰지 않는다. **네이티브 한 개 실행 성공으로 나머지 세 솔버까지 완료 처리하지 않는다.**

### 5.1 네이티브 채널

기존 metrics를 유지하되 그것만으로 이력/장이 연결됐다고 하지 않는다. 원래 raw 결과를 기준으로 선택 가능한 채널을 설명하고 읽는다. 기존 reader를 얇게 연결한다. 예전 Study/manifest만 받던 reader에는 필요한 입력을 일반 결과 참조에서 공급한다. **가짜 Study를 만들거나 기존 검사를 통째로 해제하지 않는다.**

응답마다 이름, 종류, 단위, 성분, 위치/집계, 시간축/좌표계, 원본 파일과 선택자를 유지한다. 이미 있는 공통 응답 계약을 확장하고 또 다른 결과 포맷을 만들지 않는다. 잘못된 채널은 없는 응답으로 반환하고 원인과 가능한 채널을 보여준다. 실제 하중을 기준해나 파생 충격량으로 바꿔 넣지 않는다.

긴 이력·장은 메타데이터와 참조로 유지하고 선택 범위를 읽는다. 한 job의 요약을 조회하면서 전 시간·전 요소 배열을 LLM에 넘기지 않는다. 새 결과 형식에서 동일 채널을 Python·GUI·MCP·전문가가 읽으면 같은 값을 얻어야 한다. 원래 solver가 없는 상태에서도 보관 결과를 다시 읽는다.

**필수 확인:** 실제 transient PDE 결과에서 특정 위치의 시간응답을, 실제 explicit 출력에서 물리적으로 정의한 시간 이력을 공통 response로 선택한다. 오차 scalar만 보여주는 데서 멈추지 않는다. 채널을 바꾸거나 단위를 변환한 비교에서 조건이 유지되는지 확인한다.

### 5.2 외부 솔버/결과 파일

다음 세 경로를 유지하고 연결한다. (a) 기존 ASCII/CSV/텍스트만 가져오기, (b) 후보표·입력 내보내기와 계산 결과 회수, (c) 등록된 프로그램·추출기의 자동 실행이다. LS-OPT를 사용하지 않는다. LS-DYNA의 제품별 카드/회사 라이선스 전체 지원은 후속이지만, **일반 외부 프로세스 → 실제 파일 → 곡선 → 오차 → 다음 후보**는 이번 범위다.

기존 `.k`/include 등 원본 묶음을 보존한다. 허용된 변수만 바꾸고 부속 파일을 필요한 위치에 전달한다. `$` 주석·고정폭 등 원래 덱 문법을 무작정 `string.Template`로 파괴하지 않도록 실제 형식의 입력 변경 방식을 검토한다. LLM이 매번 덱 전체나 ASCII를 다시 쓰는 경로는 만들지 않는다. 등록 명령/추출기는 운영자가 설정하고 원격 요청에서 임의 코드를 받지 않는다.

후보 ID·계수·시험조건·원본 출력의 대응을 유지한다. 누락·중복·오래된 결과, 재시작한 시간축과 섞인 채널을 구분한다. 파손 시점 등 event는 선택 응답에서 선언한 방법으로 검출하거나 추출 결과를 읽는다. 곡선+event를 동정할 때 미발생/미관측/계산 실패를 다른 상태로 처리한다.

**완료 행동:** 외부에서 만든 실제 파일을 읽고 비교·영향도에 사용한다. 별도로 등록한 실제 계산 프로그램을 실행하고, 그 출력파일을 다음 최적화 평가에 사용한다. DYNA가 없으면 공개 솔버의 ASCII 추출 또는 실제 외부 수치 실행을 사용한다. 작성한 예상 출력을 복사하는 가짜 프로세스는 외부 계산의 완료 증거가 아니다. 외부 결과를 수동 회수하는 모드도 화면에서 후보 대응과 미완료 행을 유지한다.

## 6. R3 — 전문가의 실제 도구 사용과 화면 승인을 연결한다

**수정 위치:** `caelab/assist/experts.py`, `knowledge.py`, `literature.py`, `workbench.py`, `apps/lab/workbench_routes.py`, `static/workbench.html`/`.js`, 기존 MCP 연결과 관련 테스트.

### 6.1 도구 계약을 실제 LLM에 제공

`{request: object}` 하나를 모든 도구에 적용하지 않는다. 기존 함수 시그니처/입력 모델로부터 Haystack Tool/ComponentTool 또는 검증된 스키마 생성 기능을 사용한다. 핵심은 새 schema engine이 아니라 실제 함수와 설명의 일치다. [P3]

| 도구 영역 | 반드시 설명할 입력 | 실제 반환 |
|---|---|---|
| knowledge search/source | query, collection/문서 ID 범위, locator, top_k | 읽은 구간·원문 위치·접근/추출 상태 |
| literature search/read | query/provider/filter, 논문 ID·요청 구간 | 서지·초록/원문 상태·실패·출처 |
| calculations inputs/plan | backend, settings, 변수·단위·범위, 목적/응답·제약, DOE/알고리즘, 예산 | backend 적합성, 편집할 계획, 누락 입력 |
| submit/status/result | 계획/입력 참조, 실제 job/result ID, 채널·범위 | 제출 영수증, 실제 상태, 선택 응답 |
| numerical analyze | 실제 candidate table 또는 job ID, 방법·응답·단위 | 계산한 영향도/오차, 실패율·한계 |
| experts consult | 대상 ID, 한정된 질문과 근거 참조 | 실제 자문·출처·불일치·추가 확인 |

잘못된 요청은 어떤 항목이 왜 잘못됐는지 기계적으로 읽을 수 있게 반환하고, 허용 예산 안에서 실제 모델이 수정할 수 있게 한다. 아무 인자도 없는 요청을 통과시키지 않는다. 오류 때 권한을 넓히거나 무한 재시도를 하지 않는다. 시험용 scripted generator는 단위 테스트에 남기되 실제 LLM 완료 근거로 사용하지 않는다.

### 6.2 GUI의 허용 범위와 후속 상태

사용자 화면에 자료 선택, 공개 자료 조사, 다른 전문가 자문, 계획만 작성/허용 범위에서 계산, 변수 범위·실행 수·CPU/시간을 편집하는 경로를 둔다. 기본 안전한 선택과 설명을 제공하고 수동 JSON 편집을 유일한 경로로 두지 않는다.

현재 코드의 `consult_experts`, `calculation_scope`, `transmission_scope`, `allow_generated_results`를 연결하거나, 같은 의미를 갖는 단일 공통 입력 모델로 정리한다. 이름 자체를 영구 규칙으로 만들지 않는다. 특히 다음을 지킨다.

- 사용자가 허용한 공개 조사 범위 안에서 LLM이 검색어를 만들고 발견한 논문을 읽을 수 있어야 한다. 앞으로 찾을 모든 검색어/논문 ID를 미리 수동 열거해야 하는 흐름을 없앤다. 회사 자료의 외부 전송과 공개 검색은 별도로 제어한다.
- 한 번 허용한 연구 계획의 후보마다 재승인받지 않는다. 범위·비용·자료 전송 범위가 바뀌면 변경 내용을 보여주고 필요한 확인을 받는다.
- 그 계획이 생성한 job과 결과는 해당 세션의 허용 범위에 연결한다. 다음 턴과 앱 재시작 이후에도 출처·권한을 확인해 다시 읽는다. 다른 프로젝트나 취소된 접근을 상속하지 않는다.
- 계산 제출 영수증을 실제 결과로 해석하지 않는다. 긴 solver는 job ID로 추적하고 완료 후 대화로 돌아와 결과를 읽는다. LLM 호출 제한 120초가 FE 작업 전체 완료 시간을 대신하지 않게 한다.
- 두 작업 슬롯이 전문가 대기로 점유돼 자식 계산이 시작하지 못하는 교착이 없도록 기존 작업 관리와 비동기 재개를 사용한다. 새 스케줄러를 만들지 않는다.

### 6.3 실제 모델 연결

로컬/회사 승인 endpoint 또는 기존 승인된 제공자를 사용한다. 주소·모델·인증 환경변수와 도구 호출 지원을 확인하고 최소 실제 응답 후 전체 흐름으로 간다. 제품 LLM은 개발 중인 Codex 모델·구독과 별개다. Codex 로그인만으로 앱 API가 인증됐다고 가정하지 않는다. 비밀 키를 채팅/저장소에 요청·노출하지 않는다.

현재 openai-compatible만 가능한 경로가 요구 endpoint를 못 받으면 기존 Haystack generator/integration 중 맞는 것을 선택한다. 인증이 없는 로컬 endpoint에 불필요한 비밀 키를 요구하지 않도록 실제 계약을 확인한다. 승인 없이 새 유료 API나 공개 모델로 자료를 보내지 않는다.

**완료 행동:** 사용자가 자유롭게 쓴 질문에서 실제 모델이 자료를 읽고 변수·DOE 계획을 만든다. 화면에서 계획을 편집/허용한다. 실제 계산 결과와 수치 영향도를 읽고 근거 있는 후속안을 제시한다. 다른 전문가와 실제 자문하고 불일치를 설명한다. 공개 문헌을 실제로 검색·확보·인용한다. 자료가 없거나 원문을 못 읽으면 그대로 알린다.

계정·승인 모델이 없으면 필요한 설정만 한 번 구체적으로 요청하고 다른 구현은 진행한다. **그 대기 상태에서 R3 또는 W4 전체 완료라고 보고하지 않는다.** 새 문서와 모의 답변으로 실제 연결을 대체하지 않는다.

## 7. R4 — 수치 연구의 남은 성능·일반화 문제를 해결한다

**수정 위치:** `numerical.py`, `optimizers/scipy_de.py`, `adapters/mfront_inverse.py`와 실제 MFront 준비 코드, 기존 저장·reader. 기존 SciPy/MGIS/SALib를 재사용한다.

1. MFront 일반 평가 경로에서 법칙이 공개하는 계수·이력·초기 상태를 받아 동정할 수 있게 한다. E-only/고정 이력/특정 SIF는 과거 benchmark에 남길 수 있으나 일반 연구의 입력 조건이 아니어야 한다. 실제 로딩한 법칙의 여러 계수와 서로 다른 이력으로 확인한다. FELUPE 예제를 추가한 것으로 MFront 일반화를 대신하지 않는다.
2. 준비는 작업자당 한 번, 상태는 후보·시험별로 초기화한다. 같은 이력 안의 시간증분 상태는 이어진다. 후보 A→B→A가 A 단독과 일치하는지 확인한다. native 핸들을 프로세스 간 공유하지 않는다.
3. DE의 process 설정이 실제 후보 병렬로 이어지게 기존 SciPy map/vectorized 경계를 조사해 연결한다. `updating='deferred'`, 목적·제약 평가·캐시·직렬화·취소를 함께 정리한다. 설치된 버전의 제약 평가 경로가 직렬이면 그 부분도 설명하고 실제 병렬 평가 경로를 연결한다. worker 숫자 변경만 제출하지 않는다. [P4]
4. serial/process/batch의 지원을 backend별로 정확히 표시한다. 병렬 지원이 안 되면 실행 전에 말하고 설정을 무시하지 않는다. 작은 재료점 계산은 직렬이 더 빠를 수 있으므로 배치/병렬을 강제하지 않는다.
5. 후보 수·계산 이력 길이가 늘 때 응답 복제·모든 후보 곡선의 무제한 캐시·작은 배열별 파일 증식을 점검한다. 최종/선택 후보 이력을 남기고 원본 FE 파일은 유지한다. 기록 정책과 캐시를 정리하되 계산 출처·실패 이유를 없애지 않는다.
6. 시간·메모리를 준비/실계산/기록/읽기로 구분한다. DE 실제 동시 실행은 작업자 로그와 시작/끝 구간으로 확인하고, 무거운 사례와 작은 사례를 구분한다. 허위 속도 배수를 목표로 삼지 않는다.
7. 곡선 비교 기준, 단위·좌표계·event 정의, 필터/시간 정렬·가중치는 탐색 안에서 일관되게 유지한다. 바뀌면 저장된 결과를 같은 기준으로 재평가한다. LLM이 오차를 줄이기 위해 기준을 몰래 바꾸지 않는다.

**완료 행동:** 실제 모델/출력으로 다중 계수·시험의 동정과 다른 평가기의 DOE를 수행한다. 수치 도구가 계산한 영향도와 목적값을 LLM이 읽는다. holdout과 독립 시험 확인을 구분하고, 같은 법칙의 합성 자료를 실제 재료 승인으로 해석하지 않는다. 병렬 성능 문제 하나에 전체 전문가·화면 작업을 무기한 묶지 않는다.

## 8. R5 — 실제 화면·설치·사용법을 끝까지 연결한다

**수정 위치:** 기존 `apps/lab/` 화면·routes, 업로드·미리보기·결과 선택, 기존 실행 스크립트, README와 LOCAL_EXECUTION.

한국어 파일명과 공백이 있는 경로를 받는다. 내부 저장명은 생성 ID를 쓰고 경로 구분자·상위 경로·NUL 등을 차단한다. 표시명과 실행 경로를 섞지 않는다. 큰 ASCII/native 결과는 허용된 로컬 파일 등록 또는 설정 가능한 업로드/스트리밍 경로를 제공한다. 상한만 크게 늘려 전량 읽기를 강제하지 않는다.

실제 사용자는 지원되는 작업에서 코드/JSON을 직접 수정하지 않고 파일·열·단위·응답·변수·조건을 편집할 수 있어야 한다. 채널 탐색, 비교곡선, DOE 후보·영향도, 전문가 계획의 검토·승인·수정, 자문 대상 선택, 실행 상태·중단·재열람, 보고서가 같은 실제 데이터에 연결돼야 한다. 기존 generic native JSON 입력은 고급 경로로 유지할 수 있지만 대표 사용자 흐름의 유일한 경로로 남기지 않는다.

결과 표시는 ‘설치 안 됨’, ‘실행 실패’, ‘결과 채널 미연결’, ‘모델 미설정’, ‘사용자 승인 대기’를 구분한다. 잘못된 `READY` 배지로 포장하지 않는다. 문서 검색·기존 결과 조회가 하나의 solver 실패로 함께 중단되지 않게 한다.

기존 시작 스크립트 하나와 명령/API를 활용해 로컬 서비스를 다시 켤 수 있게 한다. 현재 PC의 절대경로나 자격증명은 비공개 설정에 남기고 배포 예시에는 넣지 않는다. 사용자에게 venv·WSL·포트·솔버 변수를 매번 수동 조합하게 하지 않는다. 개발자가 실제 실행 가능한 명령과 확인한 환경을 인계한다.

MCP는 같은 job/result ID를 사용한다. SDK 시험과 실제 외부 클라이언트 시험을 구분한다. 사용 가능한 실제 클라이언트 하나에서 기존 결과를 읽고 지원 작업을 요청해 확인한다. 없는 호스트 계정 때문에 로컬 GUI를 막지는 않지만 해당 연결 미확인을 숨기지 않는다.

## 9. 종료 조건 — 실제로 보여줄 사용자 흐름

아래 흐름은 시험용 수치나 케이스 이름의 제품 제한이 아니다. 임의의 다른 자료/계수를 넣어도 공통 기능이 동작해야 한다. 실제 실행의 명령·조건·입출력·짧은 화면 기록을 남긴다. 손으로 정한 답을 보여주는 시연은 제외한다.

| 흐름 | 실제 달성할 행동 | 완료가 아닌 것 |
|---|---|---|
| A. 재료/시험 연구 | 둘 이상의 계수와 서로 다른 시험 이력으로 동정, 별도 이력 확인, 계수/곡선/잔차/한계 표시. 기존 MFront 일반 경로와 FELUPE 유지 범위를 구분 | E 하나의 합성 예제만 반복, 작은 잔차를 유일 물성으로 선언 |
| B. native 방정식/충격 | 실제 PDE 시간응답과 explicit 이력 선택·비교, 조건 변경 재실행, 새 앱에서 원본과 같은 값 확인 | solver import, 버전 출력, metrics 다섯 개만 표시 |
| C. 외부 파일 연구 | ASCII 업로드/로컬 등록→후보 대응→오차·영향도. 등록 외부 프로그램 실행→실제 출력→수치 탐색. 결과만 보는 모드는 solver 없이 재열람 | 예상 파일 복사, 새로운 후보를 실행 없이 실제값으로 표시 |
| D. 실제 전문가 연구 | 자유 질문→자료/논문 읽기→변수·범위·DOE/목적 제안→사용자 편집/허용→실제 배치→영향도 해석→다음 DOE/최적화→결과 비교 | mock/scripted 답변, 계획 JSON 출력 후 종료, LLM의 임의 영향도 점수 |
| E. 불량 자문 | 관측·변경 이력·자료와 실제 계산을 놓고 다른 전문가에게 한정 자문. 근거·반론·가설별 다음 시험과 개선안을 제시 | 여러 역할의 고정 문장, 동의를 원인 확정으로 표시 |
| F. 재개·독립 사용 | 서비스 재시작 후 원문/결과/승인된 대화 참조 복원, AI 패널 없이 계산. 실제 host 하나에서 같은 결과 조회 | Cloud 임시 파일 경로만 전달, SDK mock을 제품 host 증거로 대체 |

최종 산출물은 (1) 수정한 제품 코드, (2) 지속되는 로컬 설정/시작 경로, (3) 실제 실행 데이터와 짧은 재현 방법, (4) 관련 회귀 및 독립 검토 결과, (5) 기존 진행 기록 한 곳의 정확한 상태다. 새 보고서 분량이나 테스트 개수는 산출물을 대신하지 않는다.

상태는 기존 기록에서 **미구현 / 코드 연결 / 모의 검사 / 실제 도구 실행 / 사용자 흐름 확인 / 외부 조건 대기**를 구분하면 충분하다. 별도 상태 스키마 엔진은 만들지 않는다. 외부 조건 대기 때문에 독립 작업을 멈추지는 않지만, 남은 실제 연결이 있으면 ‘통합 완료’가 아니라 ‘부분 완료·해당 연결 대기’로 보고한다.

실제 회사 LS-DYNA 덱·라이선스, 모든 물리법칙·임의 파일 형식·HPC·시험장비 지원은 이번의 자동 완료 약속이 아니다. 반대로 기존 W1–W5의 넓은 계산/전문가 기능을 위 대표 사례로 축소하지 않는다. 형상 없는 연구와 기존 CAD·implicit·explicit 연구를 함께 살린다.

## 10. 진행 방식과 금지할 우회

시작 때 기준 main, 실제 로컬 환경, 주 담당/보조 배정, 첫 구현 순서를 짧게 보고한 뒤 구현한다. 무엇부터 할지 사용자에게 다시 정해달라고 하지 않는다. 사실은 조사하고, 구현 선택은 근거로 결정한다. 범위·비용·권한에 영향을 주는 사용자 결정만 권장안과 함께 질문한다.

각 기능 묶음의 문제를 고치고 관련 회귀를 확인한다. 전체 회귀는 통합 시점에 수행한다. 오래된 실패라는 이유로 필요한 native 기능을 방치하지 않는다. 반대로 관련 없는 구형 과학 사례 하나가 실패했다고 모든 UI/전문가 개발을 중단하지 않는다. 결과 오류를 만든 변경은 통합하지 않는다. 허용 오차 완화/검사 삭제가 필요하면 수학·물리·새 관측으로 근거를 제시한다.

독립 검토자는 실제 결과와 소비 경로를 읽고 ‘코드가 존재한다’는 주장과 구분한다. 실제 리뷰 도구를 못 썼으면 독립 리뷰를 했다고 하지 않는다. 정의된 묶음을 검토·필요 검사 후 PR로 반영한다. 사용자에게 승인받은 통합 범위에서 진행하되 보호 규칙을 우회하거나 무관한 변경을 병합하지 않는다. **병합 가능과 전체 기능 완료는 다른 판단**이다.

세션 한계에서는 기존 `WORKBENCH_PROGRESS.md`에 완료/미완료, 실행 환경, 재현 결과, 진행 중인 프로세스, 다음 수정 위치를 남긴다. 이미 사용하는 PR 진행 댓글이 원본이면 그곳 하나를 사용하고 파일에는 링크만 둔다. 같은 내용을 여러 위치에 복제하지 않는다. 보조·솔버를 안전하게 정리하고 다음 세션이 코드 지점에서 이어가도록 한다. 자동 재개를 실행하지 않았으면 약속하지 않는다.

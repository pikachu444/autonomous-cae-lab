# CAE 연구 작업대 — 재설계와 구현 계획

기준일: 2026-10-07. 검토 기준: `main@4843c66e482ded31c59604d7cc19d1800be388f4`.
상태: 사용자 요구를 반영한 재설계 기준과 개발 지침 정리. 런타임 개편은 아직 미구현.

## 1. 만들려는 것과 만들지 않을 것

연구자가 자신의 계산 코드, 재료모델, 솔버, 시험 데이터와 자료를 연결해
질문을 탐구하는 가벼운 로컬 연구 작업대다. 거대한 SPDM, 새 솔버, 새 최적화
알고리즘, 새 에이전트 운영체제를 만드는 프로젝트가 아니다.

Python/API와 CLI에서 AI·OpenScience·MCP 없이 직접 사용할 수 있어야 한다.
설치된 로컬 계산은 인터넷 없이 수행할 수 있어야 한다. GUI와 자연어 전문가,
RAG, 논문 검색, MCP는 필요에 따라 연결한다. 외부 서비스가 필요한 기능까지
오프라인으로 된다고 주장하지 않는다.

범위는 CAD 설계뿐 아니라 재료 평가·물성 동정·구성모델 연구, PDE·약형,
선형/비선형 구조·접촉·큰 변형·implicit/explicit·손상, 시험/기존 결과 분석,
DOE·최적화·역문제·UQ·감도·대리모델·연성 문제·수치 알고리즘 연구를 포함한다.
모든 분야를 이번에 구현했다는 뜻은 아니다. 첫 사례가 전체 범위를 제한해서는
안 된다. 향후 계산장비/시험장비 연결은 실제 필요에 따라 추가한다.

사용자가 승인한 변경 방향: 잘못된 프로필·문서·테스트·개발 기록의 하위호환성을
무조건 유지하지 않는다. 대신 실제 사용자 자료, 유용한 수치 기준과 현재 편집
작업은 보호한다. 옛 52개 항목의 세부 대조는 이번 핵심 경로 검토에서 완료하지
않았으며, 과거 목록은 누락 점검에 참고하되 낡은 실행 순서를 강제하지 않는다.

## 2. 확인한 사실과 앞선 설명의 정정

이번 검토는 공개된 코드의 핵심 경로와 개발 지침을 읽은 정적 검토다.
로컬 미커밋 작업, 전체 파일의 전수 검증, 솔버 실행, GUI 및 성능 측정은 하지
않았다. 기록에 적힌 과거 실행은 이번 실행으로 다시 인정하지 않는다.

| 확인 사항 | 근거 | 판단 |
|---|---|---|
| CAD 없는 실행 경계가 이미 있다 | `caelab/contracts.py`: `ModelAnalysisAdapter`, `PDEAdapter`, `ParameterizedModelAdapter` | 새로 발명하지 말고 일반 사용 경로를 개선한다 |
| 최적화는 SciPy를 실제 사용한다 | `caelab/optimizers/scipy_de.py`: `differential_evolution`, `qmc` | 자체 최적화 알고리즘으로 오해하지 않는다 |
| 병렬/배치 실행이 고정 제한돼 있다 | 같은 파일의 `workers=1`, `vectorized=False` | 호환성·상태 분리를 확인하고 선택 가능하게 한다 |
| 코어도 특정 구현과 결합돼 있다 | `caelab/engine.py`의 구체 어댑터 import와 기본 생성 목록 | 선택적 로딩·등록·설치 경계를 정리한다 |
| 프로필이 역할을 너무 많이 섞는다 | `scripts/openscience-research.ps1`의 9개 프로필, 입력·도구·경로·예산·설명 | 권한, 설치, 계산 조건, 전문가 정의를 분리한다 |
| MCP 안에 특정 AI 사용 제한이 있다 | `openscience/mcp_server.py::optimization_run` | 전송 계층에서 공학 실행 정책을 제거한다 |
| 재료 동정도 특정 예제/설치에 고정된다 | `caelab/adapters/mfront_inverse.py`의 E-only 제한과 바이너리 지문 | 예제 검증과 일반 기능·설치 확인을 분리한다 |
| 파일 확인 비용이 커질 수 있다 | `caelab/storage.py`의 전체 파일 `read_bytes`, 전체 Core 재검색 | 호출 횟수·읽은 바이트·메모리를 측정한 뒤 개선한다 |
| 개발 지침이 과거 보존을 강제했다 | 이전 `AGENTS.md`, 프로필 검증 스크립트 | 이 브랜치의 지침으로 대체한다 |
| 최근 계획은 이미 지엽적 개발을 비판한다 | `docs/CAE_RESEARCH_EXECUTION_PLAN.md` 최신 부분 | 새 원칙 발명보다 상충 지침을 정리한다 |

코어가 완벽하거나 모든 관리 코드가 불필요하다고 단정하지 않는다. 파일 잠금,
원자적 저장, 출처 확인과 작은 연결 코드는 필요할 수 있다. 단위 테스트와 소스
검사도 유효하다. 없앨 것은 목적을 잃은 계약이지 검사 종류 전체가 아니다.

## 3. 목표 구조

```text
Python / CLI / 선택적 GUI / 선택적 MCP / 선택적 OpenScience
                         │
              공통 작업 API와 결과 읽기
                         │
       계산 입력 → 평가/실행 → 응답과 선택적 실행 기록
                         │
       기존 Python·재료·PDE·FE·후처리 어댑터/라이브러리
```

전문가 기능은 공통 작업 API, 내부 자료 검색, 논문 검색을 사용한다. 코어는
전문가나 모델 인증을 몰라도 동작한다. 개발용 grill-me/Ouroboros/검색 스킬은
이 제품 계층 밖에 둔다.

매번 Study·가설·파일 저장을 요구하지 않는다. 빠른 함수 평가와 일회성 데이터
분석은 직접 실행할 수 있고, 연구자가 묶어 비교할 때 연구/실행 기록을 붙인다.
기존 실험 API를 활용하되 새 만능 스키마나 병렬 프레임워크를 먼저 만들지 않는다.

공통 결과는 값뿐 아니라 단위, 시간축, 성분, 위치/영역, 집계 방식과 상태를
전달한다. 곡선/장은 배열 또는 결과 파일 참조로 유지한다. 원본 형식이 필요한
전문 작업은 원본과 특정 솔버 설정으로 내려갈 수 있어야 한다.

### 빠른 계산과 오래 걸리는 계산

재료 동정은 초기화/컴파일을 재사용하고 후보를 메모리·배치로 평가한다. 이력
의존 재료는 후보마다 상태를 올바르게 초기화한다. LLM·파일 기록·컨테이너 시작을
수치 루프마다 수행하지 않는다. 후보 요약과 필요한 중간 저장을 연구 단위로 묶는다.

FE 계산은 실행별 작업 폴더와 CPU·메모리 요구를 갖고 독립 실행한다. 짧은 결과
등록은 잠글 수 있지만 전체 계산을 단일 작성자 잠금에 가두지 않는다. 중단·실패·
재시작은 실제 소유한 작업을 기준으로 처리한다. 작업 관리 라이브러리 도입만으로
외부 솔버의 종료/복구 문제가 해결됐다고 보지 않는다.

### 과도한 검증 규칙 정리

소프트웨어 동작, 수치 신뢰성, 실제 제품 승인 상태를 구분한다. 연구 목적에 맞는
확인만 요청하며 모든 탐색에 강도 승인·다중 메시 검증을 강제하지 않는다. 미확인
사항은 표시하되 올바른 탐색 자체를 막는 만능 거부 사유로 사용하지 않는다.

입력 범위, 파일 권한, 비용/자원 제한과 사용자 데이터 보호는 유지한다. 과거
프롬프트·프로필 지문 보존은 기본 개발 목표에서 제외한다. 중요한 입력/결과의
지문은 식별·손상 확인·재사용에 쓰되 매 호출 전체 재검증을 기본으로 삼지 않는다.

## 4. 외부 기술 선택

현재 기본은 이미 쓰는 Python·NumPy/SciPy와 기존 어댑터를 살리는 것이다.
프레임워크 도입 자체를 개선 실적으로 세지 않는다.

| 영역 | 우선 판단 | 도입/교체 조건 |
|---|---|---|
| DOE·단일 최적화·동정 | 기존 SciPy 사용 유지·간소화 | 최소제곱/배치/병렬 등 실제 문제의 알고리즘과 제약에 맞춰 확장 |
| 공통 연구 조합 | GEMSEO와 OpenMDAO를 필요 시 비교 | 기존 코드보다 모델 연결/미분/기록 중복을 실제 줄이는지 같은 사례로 확인 |
| 다목적·UQ | pymoo/SALib/DAKOTA 등 해당 요구에 맞는 후보 | 필요한 방법이 기존 경로에 없을 때만 선택; 모두 필수 설치하지 않음 |
| 로컬 병렬 | 표준 실행기 또는 joblib 등 작은 재사용 | 외부 프로세스·메모리·코어 수와 재료 상태 독립성 확인 |
| HPC/복잡한 장기 워크플로 | 별도 수요가 생길 때 과학계산 실행 도구 비교 | AiiDA/Parsl 등 전체 체계를 초기 필수 기반으로 넣지 않음 |
| 자료 검색 | 기존 검색/문서 처리 구성요소 재사용 | 작은 사내 문서 묶음의 정답 근거·페이지 추적·검색 품질로 선택 |
| 전문가 실행 | 기존 호스트/에이전트 기능 활용 | OpenScience 버전별 실제 동작 확인; 새 에이전트 OS 구축 금지 |
| MCP | 기존 공식 SDK 연결 유지 | 동일 API, 권한, 장기 작업·파일 전송·클라이언트 호환성 시험 |

참고한 실제 upstream: [SciPy DE](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.differential_evolution.html),
[GEMSEO](https://gemseo.readthedocs.io/en/stable/),
[OpenMDAO DOE](https://openmdao.org/newdocs/versions/latest/features/building_blocks/drivers/doe_driver.html),
[joblib 설정](https://joblib.readthedocs.io/en/stable/generated/joblib.parallel_config.html),
[Haystack BM25](https://docs.haystack.deepset.ai/docs/inmemorybm25retriever),
[OpenScience](https://github.com/synthetic-sciences/openscience).
문서 확인과 실제 이 저장소 호환성 검증은 다르다. 위 후보를 설치하거나
성능 비교하지 않았다. 미검증 후보의 채택은 확정하지 않는다.

## 5. 전문가·지식·문헌

전문가 정의는 역할, 참고 지식 범위, 허용 도구, 응답 기준을 담는다. 모델과 인증은
별도 실행 설정이다. 명시한 전문가를 우선하며 필요할 때만 다른 전문가를 호출한다.
단순 질문마다 여러 에이전트가 토론하게 하지 않는다.

내부 자료 검색과 외부 논문 검색은 별개로 둔다. 정확한 코드/재료/표준 식별자와
의미 검색을 함께 평가한다. 출처·문서 버전·페이지/구간을 답에 붙이고 초록만 읽은
논문을 원문 분석으로 쓰지 않는다. 검색 결과의 임시 보관과 승인된 지식 편입을
구분한다. 프로젝트 결정과 대화는 원자료와 섞어서 사실로 학습시키지 않는다.

MCP에서는 직접 검색·계산·결과 읽기를 먼저 제공한다. 내부 전문가 실행까지
위임하는 도구는 필요할 때 별도로 추가하며 별도 모델 호출 비용/시간/취소가 생김을
명시한다. MCP만 붙인다고 모든 클라이언트의 로컬 파일·실행 권한이 같아지지 않는다.

OpenScience upstream README는 Apache-2.0과 여러 모델/확장 경로를 명시한다.
그러나 사용 중인 고정 버전, 번들 구성요소, 외부 인증/API는 따로 검증해야 한다.
검증한 소스/설치본과 의존성을 보관하고, OpenScience를 지워도 직접 계산과 기록
읽기가 되는 경로로 종속 위험을 줄인다.

## 6. 성능과 실제 사용 기준

성능 개선 전 직접 라이브러리 실행과 현행 경로를 같은 입력으로 비교한다.
콜드 시작, 준비/컴파일, 순수 계산, 기록/검증 I/O, 결과 읽기를 따로 측정한다.
대표 검사는 짧은 재료 배치, 기존 native solve, 큰 결과 읽기, 독립 실행 병렬이다.

수치 루프의 후보당 LLM 호출은 0이어야 한다. 나머지 시간·메모리 목표는 실측
후 정한다. 미리 임의 초/배율을 통과 규칙으로 박지 않는다. 읽기 전용 화면을
열 때 해석이 재실행되거나 설치된 모든 솔버가 시작되어서는 안 된다.

초기 기능 확인은 서로 다른 세 경로로 한다: (1) CAD 없는 재료/데이터 평가,
(2) 기존 PDE 또는 FE 실행과 결과 재열람, (3) 기존 결과·문헌 근거를 읽는 전문가.
세 번째는 첫 두 경로 전체의 실물 승인과 무관하게 읽기 전용으로 개발할 수 있다.
추가 기능 시에는 실패 입력, 단위/성분 불일치와 중단도 해당 범위에서 확인한다.

| R1 · 독립 사용과 확장 | 패키징/선택적 어댑터 생성/직접 평가 진입점/기존 설치 안내 | 새 환경에서 필요한 구성만 설치. AI/MCP/CAD 없이 기존 비-CAD 기능 실행. 외부 사용자 함수 또는 재료 입력 하나 추가 시 프로필·JS·PS 동시 편집 불필요 |
| R2 · 계산·기록 비용 | 기존 SciPy 경로, 파일 읽기/기록, 실행 자원/중단 | 같은 응답을 유지하며 직접 계산 대비 비용표 제출. 배치·독립 작업 병렬, 코어 과할당 방지, 실패 격리, 짧은 기록 잠금 확인 |
| R3 · 연결 정책 정리 | research profile/guard, MCP, 모델·설치 경로, 관련 테스트 | 과거 시나리오 프로필 제거/단순화. 같은 권한이면 직접/API/MCP가 같은 계산 가능. 설치 경로 변경 때문에 물리 코드 수정 불필요 |
| R4 · 전문가와 근거 | 기존 호스트와 검색 구성요소, 전문가 선택·출처·결과 조회 | 전문가 지정→내부 근거 검색→필요한 외부 조사→실제 결과 읽기→출처 있는 답변. 새 프레임워크 없이 증명 |
| R5 · 업무 파일럿 | 사용자 실제 데이터/계산 절차·설치/보안·사용성 | 입력→연구→재열람/수정→공유 가능한 결과까지 실행. 절감 시간·실패율·수정 부담을 수작업 기준과 비교 |

R0은 이 브랜치의 문서 변경이다. R1–R5를 완료했다고 표시하지 않는다.
R1 다음에 또 새로운 감사 문서나 전용 스킬을 만드는 것이 아니라 해당 코드를
개선하고 실행한다. 검색/설계는 필요한 결정에 한정한다. R4 읽기 전용 작업은
독립 진행 가능하지만 공통 API 변경은 한 소유자가 통합한다.

옛 프로필 지문 테스트는 그 실행 경로를 대체하는 묶음에서 제거한다. 계산 기준,
상태 초기화, 단위/부호, 실패와 사용자 데이터 보호는 새 동작 검사로 유지한다.
실사용 자료의 이관이 필요한 경우에만 이관 코드를 만든다. 재현할 필요 없는
개발 기록 때문에 제품에 영구 호환 계층을 추가하지 않는다.

## 8. 개발 도구를 또 제품으로 만들지 않기

기존 [grill-me/grilling](https://github.com/mattpocock/skills/tree/main/skills/productivity),
[search-first](https://github.com/affaan-m/ECC/blob/main/.kiro/skills/search-first/SKILL.md),
[Ouroboros](https://github.com/Q00/ouroboros)는 개발 지원 후보다. 현재 grill-me가
다른 스킬로 위임하는 구성, search-first의 호스트별 변형처럼 실제 파일과
의존성을 확인한다. 이번에 설치/통합한 것으로 간주하지 않는다.

이미 대화에서 정한 목표를 다시 인터뷰하지 않는다. 저장소/문서에서 알아낼 수
있는 사실은 조사하고, 사용자만 정할 수 있는 고비용 결정만 질문한다. 작은 버그
수정에 전체 인터뷰·스킬 체계·재설계 절차를 강요하지 않는다.

매 묶음 종료 시 질문은 하나다. “서로 다른 연구를 더 적은 설정과 관리 코드로
수행하게 됐는가, 아니면 새 예외와 승인 절차만 늘었는가?” 답은 코드 변경과
실제 사용 결과로 제시한다.

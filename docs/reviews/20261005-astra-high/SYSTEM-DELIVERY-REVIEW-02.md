# 전체 시스템·사용자 전달 방식 후속 독립 의견

2026-10-05 · GPT-6 Astra/high · 기존 Main815 전체 감사를 재사용한 후속 평가

**사용자의 지적이 맞다. 아키텍처의 큰 방향은 적절하지만, Root는 “사용자가 연구를 끝낼 수 있게 만드는 일”보다 작은 검증 단위를 닫고 재감수를 받는 일에 치우쳤다. 이번 문제는 추가 코드 감수가 부족해서가 아니라, Root가 작업 단위와 완료 기준을 잘못 운영한 데 있다.** 현재 판정은 여전히 **운영자 지원이 필요한 제한된 연구 프로토타입**이다. 전체 서비스 완료나 일반 CAE 연구의 자율 수행을 주장할 근거는 없다.

## 1. 전체 구성은 유지하되, 연결과 운영을 완성해야 한다

OpenScience가 질문·가설·캠페인 선택과 해석을 맡고, Core가 공통 입력·실행 차단·실험/개정·증거를 관리하며, Domain이 공학적 의미와 판정을, adapter가 CAD/솔버 문법을, 수치 엔진이 후보 생성·탐색을 맡는 분리는 타당하다. 사람 화면과 AI가 같은 모델·결과를 보는 원칙도 맞다. 시스템을 다시 만들거나 연구 모델·솔버를 바꾸는 것이 해결책은 아니다.

부족한 것은 이 경계들 사이의 **완성된 사용자 계약**이다. 사용자는 지원 질문을 고르고, 필요한 가정을 이해하고, 조건을 바꾸고, 작업 상태를 믿고, 같은 기록의 결과를 비교해야 한다. 지금은 공통 Core의 연결보다 프로필별 승인·운영자 설정·개별 검증 기록이 사용 흐름을 설명하는 비중이 크다. descriptor의 엄격함은 유지하되 이를 사용자가 내부 스키마를 이해해야 하는 부담으로 전가해서는 안 된다.

또한 “구현됨”, “현재 실행 가능”, “이 사례에서 수치 검증됨”, “사용자가 끝까지 사용해 봄”, “실물 사용 승인”은 서로 다르다. 현재 기능 목록·진행 보고의 중심은 첫 항목에서 네 번째 항목으로 옮겨야 한다. NOT_RELEASED여도 가정과 유효 응답이 명확한 가상 연구는 가능하다. 강도·실물 승인까지 없다는 이유로 그런 연구 연결을 계속 미루어서는 안 된다.

## 3. Root의 전달 방식에 대한 비판

- **감수 요청의 목적을 잘못 번역했다.** 사용자는 전체 시스템과 일을 진행하는 방식을 평가받으라고 했는데, 실제 후속 요청은 full-field source, native output, selected mode, guard, Research source, CI 인자 추가 등 작은 패킷으로 이어졌다. 각 검토가 정확해도 사용자가 요청한 전체 평가를 대신하지 못한다. 검토 범위를 정하는 것은 Root의 책임이다.
- **통합 책임을 반복 감수로 분산시켰다.** GUI가 source PASS 뒤 실제 화면에서 실패할 수 있는 것은 자연스럽다. 그러나 가려진 표시→render failure→빈 입력 교정마다 Astra를 다시 통과해야 다음 사용자 흐름으로 가는 구조는 과하다. Root가 기본 상호작용을 직접 확인하고 한 번의 완성된 교정 묶음을 책임졌어야 한다. 독립 검토는 중요한 공통 경계나 실제 연구 결과의 해석을 점검할 때 가치가 크다.
- **작은 완료가 실제 완료를 가렸다.** 소스·manifest·receipt·문서가 계속 확정되는 동안 공식 새 프로필의 폭38 연구, 조건 변경 비교, S3 복구, U1은 열린 채였다. 기존815 감사가 이미 같은 문제를 지적했는데도 작업 방식은 충분히 바뀌지 않았다. 이는 단순히 신중한 검증의 비용으로 설명할 문제가 아니다.
- **계획의 순차 의존성을 과도하게 적용했다.** Results 화면의 모든 작은 수정이 끝날 때까지 첫 짧은 selected Research 연결을 미루고, S3 전체 완료 전에는 U1의 어떤 부분도 실행하지 않는 식이면 병목이 반복된다. 짧은 감독 실행으로 질문→32/38 비교 부분을 먼저 닫고, 복구가 필요한 긴 탐색·무감독 인계만 S3에 묶을 수 있다. 전체 U1 완료 표시는 마지막에 한다.
- **진척 보고의 단위가 사용자에게 맞지 않았다.** “몇 파일/몇 테스트/몇 건 독립 PASS”는 근거이지 사용자가 얻은 기능이 아니다. 먼저 “이 질문을 이제 끝낼 수 있다/이 단계에서 막힌다”를 말하고, 그 뒤 해당 증거 하나를 제시해야 한다. 많은 설명과 보존 작업이 다음 사용 가능한 결과를 대신해서는 안 된다.

이번 검토자 역시 받은 작은 범위에 맞춰 여러 PASS를 반환했다. 그 판정은 해당 범위에 한정되며 전체 시스템이나 Root 수행 방식의 승인으로 사용하면 안 된다. 필요한 교정은 더 많은 Astra 호출이 아니라 **Root가 사용자 흐름을 소유하고 끝내는 운영 방식**이다.

## 5. 지금 중단·유지·앞당길 것

**중단:** 작은 UI 입력/표시 수정마다 새로운 Astra 승인 대기, 증거 변화 없는 전수 재감사, 같은 현재 상태를 여러 문서에 장문 복제, 원인 가설 없는 반복 native/CI 실행, 모든 세부 gate가 끝날 때까지 사용자 실행을 미루는 방식. 최신 writer03의 통과 수를 다시 감수받는 것이 다음 사용자 산출물은 아니다.

**유지:** pinned upstream와 계층 경계, 결정론적 수치 엔진, 승인5.6Sol/기존 OAuth, source/입력/개정 연결, 소비 시 필요한 artifact 무결성, 잘못된 입력의 native 차단, 실패·invalid·UNKNOWN·NOT_RELEASED, 중요한 공통 계약과 대표 수치 결과에 대한 독립 검토. 검증을 없애거나 수치 문턱을 낮추라는 의견이 아니다.

**앞당김:** Root 자신의 통합/화면 점검, 공식 selected Research의 실제 폭 변경 질문, 같은 기록의 비교·재열람, S3 최소 복구 구현, 실패한 CI의 expected/actual/raw 원인 분리. 사용자가 다음에 받아야 할 것은 또 하나의 작은 PASS 목록이 아니라 **직접 따라 할 수 있는 첫 연구와 아직 막힌 한두 단계의 정확한 설명**이다.
